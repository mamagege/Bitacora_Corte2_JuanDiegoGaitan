Paso 2 — Autenticación más simple
HTTP Basic — usuario y contraseña en cada petición

HTTP Basic es el primer nivel de autenticación. El cliente envía usuario:contraseña codificados en Base64 en el header Authorization en cada petición. Es stateless — el servidor no guarda sesión. Sirve para entender la mecánica antes de pasar a JWT.

⚠️
HTTP Basic no cifra — solo codifica. Base64 es reversible en un segundo. HTTP Basic solo es seguro sobre HTTPS. Nunca lo usen en producción sin SSL. En este sprint lo usan para aprender el flujo — JWT es el estándar real.
Flujo de HTTP Basic
sequenceDiagram participant C as Cliente participant S as Spring Security Filter participant U as UserDetailsService participant A as API Controller C->>S: GET /api/v1/platos
Authorization: Basic dXN1YXJpbzpjbGF2ZQ== S->>S: Decodifica Base64 → usuario:clave S->>U: loadUserByUsername("usuario") U-->>S: UserDetails (roles, password hash) S->>S: BCrypt.matches(clave, hash) → true/false alt Autenticado S->>A: Pasa la petición A-->>C: 200 OK + datos else No autenticado S-->>C: 401 Unauthorized end

  1. Crear el modelo de Usuario con roles
@Entity @Table(name = "usuarios")
public class UsuarioEntity {
    @Id @GeneratedValue
    private Long id;
    @Column(unique = true, nullable = false)
    private String email;
    private String password;   // SIEMPRE hasheado con BCrypt — nunca en texto plano
    private String rol;        // "ROLE_ADMIN", "ROLE_CHEF", "ROLE_CLIENTE"
}
  1. Implementar UserDetailsService
    Spring Security necesita saber cómo cargar un usuario por nombre. Esta implementación lo busca en su BD:
@Service @RequiredArgsConstructor
public class UsuarioDetailsService implements UserDetailsService {

    private final UsuarioRepository repository;

    @Override
    public UserDetails loadUserByUsername(String email) throws UsernameNotFoundException {
        UsuarioEntity usuario = repository.findByEmail(email)
                .orElseThrow(() -> new UsernameNotFoundException("Usuario no encontrado: " + email));
        return User.builder()
                .username(usuario.getEmail())
                .password(usuario.getPassword())     // ya viene hasheado de la BD
                .roles(usuario.getRol())             // "ADMIN", "CHEF", "CLIENTE"
                .build();
    }
}
  1. Configurar SecurityConfig con HTTP Basic
@Configuration @EnableWebSecurity @EnableMethodSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        return http
            .csrf(csrf -> csrf.disable())           // APIs stateless no necesitan CSRF
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/v1/platos").permitAll()             // carta pública
                .requestMatchers("/swagger-ui/**", "/v3/api-docs/**").permitAll() // Swagger
                .requestMatchers(HttpMethod.POST, "/api/v1/platos").hasRole("CHEF")
                .anyRequest().authenticated()
            )
            .httpBasic(Customizer.withDefaults())   // activa HTTP Basic
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .build();
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();  // OBLIGATORIO — nunca guardar passwords en texto plano
    }
}
  1. Registrar usuario con password hasheado
    En el endpoint de registro, hasheen el password antes de guardarlo:
// En el ServiceImpl de registro:
public Usuario registrar(Usuario usuario) {
    usuario.setPassword(passwordEncoder.encode(usuario.getPassword()));  // ← siempre
    return mapper.toDomain(repository.save(mapper.toEntity(usuario)));
}
  1. Probar en Swagger — agregar el botón Authorize
    Swagger necesita conocer el esquema de autenticación para mostrar el candado. En SwaggerConfig.java:
@Bean
public OpenAPI openAPI() {
    return new OpenAPI()
        .info(new Info().title("API Restaurante").version("2.0"))
        .addSecurityItem(new SecurityRequirement().addList("basicAuth"))
        .components(new Components()

                new SecurityScheme().type(SecurityScheme.Type.HTTP).scheme("basic")));
}

Paso 3 — Autenticación con proveedor externo
OAuth2 — "Ingresar con Google"

OAuth2 permite que sus usuarios se autentiquen usando Google, GitHub u otro proveedor de identidad, sin que su API maneje contraseñas directamente. El proveedor confirma la identidad — su API solo recibe un token válido.

Flujo completo OAuth2 con Google
sequenceDiagram participant U as Usuario/Browser participant A as Su API Spring Boot participant G as Google OAuth2 U->>A: GET /oauth2/authorization/google A-->>U: Redirect → accounts.google.com?client_id=...&redirect_uri=... U->>G: El usuario ingresa sus credenciales de Google G-->>U: Redirect → /login/oauth2/code/google?code=ABC123 U->>A: GET /login/oauth2/code/google?code=ABC123 A->>G: POST /token con code=ABC123 + client_secret G-->>A: access_token + id_token (JWT con info del usuario) A->>A: Crea/actualiza el usuario local con los datos de Google A-->>U: Sesión establecida — redirige a la app

        OAuth2User oauthUser = (OAuth2User) authentication.getPrincipal();
        String email = oauthUser.getAttribute("email");
        String nombre = oauthUser.getAttribute("name");
        // Crear o actualizar el usuario en su BD con email y nombre de Google
        // Luego generar un JWT propio y devolverlo (ver sección JWT)
        log.info("Login OAuth2 exitoso: {}", email);
        response.sendRedirect("/api/v1/auth/me");
    };
}

💡
Patrón común — OAuth2 + JWT: en la mayoría de proyectos reales, OAuth2 autentica al usuario con Google, y luego el successHandler genera un JWT propio de su sistema y lo devuelve al cliente. El cliente usa ese JWT en las siguientes peticiones. Así combinan OAuth2 (identificación con proveedor externo) con JWT (sesión stateless en su API).

⚙️ Fase 2 — JwtUtil: generar y validar tokens

@Component
public class JwtUtil {

    @Value("${jwt.secret}")          private String secret;
    @Value("${jwt.expiration-ms}")    private Long expirationMs;

    private SecretKey getKey() {
        return Keys.hmacShaKeyFor(Decoders.BASE64.decode(secret));
    }

    public String generateToken(String email, String rol) {
        return Jwts.builder()
                .subject(email)
                .claim("rol", rol)
                .issuedAt(new Date())
                .expiration(new Date(System.currentTimeMillis() + expirationMs))
                .signWith(getKey())
                .compact();
    }

    public Claims extractClaims(String token) {
        return Jwts.parser()
                .verifyWith(getKey()).build()
                .parseSignedClaims(token)
                .getPayload();
    }

    public boolean isValid(String token) {
        try {
            extractClaims(token);
            return true;
        } catch (JwtException | IllegalArgumentException e) {
            return false;
        }
    }
}

🔍 Fase 3 — JwtAuthFilter: interceptar cada petición

@Component @RequiredArgsConstructor
public class JwtAuthFilter extends OncePerRequestFilter {

    private final JwtUtil jwtUtil;
    private final UsuarioDetailsService userDetailsService;

    @Override
    protected void doFilterInternal(HttpServletRequest req,
                                      HttpServletResponse res,
                                      FilterChain chain) throws IOException, ServletException {

        String header = req.getHeader("Authorization");
        if (header == null || !header.startsWith("Bearer ")) {
            chain.doFilter(req, res); return;
        }

        String token = header.substring(7);
        if (jwtUtil.isValid(token)) {
            String email = jwtUtil.extractClaims(token).getSubject();
            UserDetails user = userDetailsService.loadUserByUsername(email);
            UsernamePasswordAuthenticationToken auth =
                    new UsernamePasswordAuthenticationToken(user, null, user.getAuthorities());
            auth.setDetails(new WebAuthenticationDetailsSource().buildDetails(req));
            SecurityContextHolder.getContext().setAuthentication(auth);
        }
        chain.doFilter(req, res);
    }
}

📡 Fase 4 — AuthController: login devuelve el token

@RestController @RequestMapping("/api/v1/auth") @RequiredArgsConstructor
public class AuthController {

    private final AuthenticationManager authManager;
    private final JwtUtil jwtUtil;

    @PostMapping("/login")
    public ResponseEntity<TokenResponseDTO> login(@RequestBody LoginRequestDTO dto) {
        Authentication auth = authManager.authenticate(
                new UsernamePasswordAuthenticationToken(dto.email(), dto.password()));
        UserDetails user = (UserDetails) auth.getPrincipal();
        String token = jwtUtil.generateToken(user.getUsername(),
                user.getAuthorities().iterator().next().getAuthority());
        return ResponseEntity.ok(new TokenResponseDTO(token));
    }
}

// Records para los DTOs
public record LoginRequestDTO(String email, String password) {}
public record TokenResponseDTO(String token) {}

Paso 5 — ¿Qué puede hacer cada usuario?
Autorización — permisos por endpoint y por método
💡
Autenticación vs Autorización: Autenticación = ¿quién eres? (ya resuelta con JWT). Autorización = ¿qué puedes hacer? (se configura aquí). Una vez que el JwtAuthFilter establece la identidad del usuario, Spring Security evalúa si ese usuario tiene el rol necesario para ejecutar la acción.

Forma 1 — Reglas en SecurityConfig (por URL)

.authorizeHttpRequests(auth -> auth
    .requestMatchers(HttpMethod.GET, "/api/v1/platos").permitAll()
    .requestMatchers(HttpMethod.POST, "/api/v1/platos").hasRole("CHEF")
    .requestMatchers("/api/v1/pedidos/**").hasAnyRole("CLIENTE", "MESERO")
    .requestMatchers("/api/v1/admin/**").hasRole("ADMIN")
    .anyRequest().authenticated()
)

Forma 2 — @PreAuthorize en el método (más granular)

@RestController
public class PlatoController {

    @GetMapping    // sin restricción — público
    public List<PlatoResponseDTO> listar() { ... }

    @PostMapping
    @PreAuthorize("hasRole('CHEF')")   // solo el chef crea platos
    public ResponseEntity<PlatoResponseDTO> crear(...) { ... }

    @DeleteMapping("/{id}")
    @PreAuthorize("hasRole('ADMIN') or hasRole('CHEF')")
    public ResponseEntity<Void> eliminar(@PathVariable Long id) { ... }

    @PatchMapping("/{id}/estado")
    @PreAuthorize("hasAnyRole('MESERO','CHEF')")
    public ResponseEntity<PlatoResponseDTO> actualizarEstado(...) { ... }
}

@ExceptionHandler(AccessDeniedException.class)
@ResponseStatus(HttpStatus.FORBIDDEN)

}

Paso 6 — Cifrado en tránsito
SSL/TLS — de HTTP a HTTPS

SSL cifra todo lo que viaja entre el cliente y el servidor. Sin HTTPS, un atacante en la red puede ver los tokens JWT en texto plano. En desarrollo usan un certificado auto-firmado. En producción usan Let's Encrypt o el certificado de Azure.

  1. Generar certificado auto-firmado para desarrollo
# Ejecutar en la raíz del proyecto
keytool -genkeypair -alias restaurante -keyalg RSA -keysize 2048 \
  -storetype PKCS12 -keystore src/main/resources/restaurante.p12 \
  -validity 365 \
  -dname "CN=localhost, OU=Dev, O=Restaurante, L=Bogota, S=DC, C=CO"
# Les pedirá una contraseña — guárdenla para el application.yml
# application.yml
server:
  port: 8443
  ssl:
    key-store: classpath:restaurante.p12
    key-store-password: ${SSL_KEYSTORE_PASSWORD}
    key-store-type: PKCS12
    key-alias: restaurante
⚠️
El archivo .p12 y la contraseña no van en Git. Agréguenlo a .gitignore. En CI/CD y en producción se inyecta como variable de entorno o secreto.
✅
Verificación: levanten la app → abran https://localhost:8443/swagger-ui/index.html. El navegador mostrará "advertencia de certificado" (es auto-firmado) → hagan clic en "Avanzado" → "Continuar". Deben ver Swagger en HTTPS.

Paso 7 — Acceso desde el frontend
CORS — quién puede llamar a su API desde un navegador

Sin CORS configurado, su frontend React en localhost:3000 no puede llamar a su API en localhost:8080 — el navegador bloquea la petición. CORS le dice al navegador qué dominios externos tienen permiso de hacer peticiones a su API.

@Configuration
public class CorsConfig {

    @Bean
    public CorsConfigurationSource corsConfigurationSource() {
        CorsConfiguration config = new CorsConfiguration();
        config.setAllowedOrigins(List.of(
            "http://localhost:3000",     // frontend React en desarrollo
            "https://su-dominio.com"      // producción
        ));
        config.setAllowedMethods(List.of("GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"));
        config.setAllowedHeaders(List.of("*"));
        config.setAllowCredentials(true);   // necesario para enviar cookies o Authorization headers

        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        source.registerCorsConfiguration("/**", config);
        return source;
    }
}

// En SecurityConfig, activar CORS:
http.cors(cors -> cors.configurationSource(corsConfigurationSource()))
🚨
NUNCA usen allowedOrigins("*") con allowCredentials(true). El navegador rechaza esta combinación por seguridad. Si necesitan aceptar cualquier origen durante desarrollo, usen allowedOrigins("*") SIN allowCredentials(true).

Paso 8 — Checklist de vulnerabilidades
OWASP Top 10 — evalúen su API

OWASP publica las 10 vulnerabilidades más críticas en APIs. Revisen su código contra este checklist antes de presentar. Cada ítem con ☐ es algo que deben verificar y corregir si aplica.

A1
Broken Access Control — Control de acceso roto

¿Pueden sus endpoints ser accedidos por roles que no deberían? Prueben llamar a POST /platos con un token de CLIENTE — deben recibir 403. Si reciben 200, tienen A1.

A2
Cryptographic Failures — Fallas criptográficas

¿Los passwords se guardan con BCrypt? ¿El JWT usa HS256 con un secret de al menos 44 chars Base64? ¿La app corre en HTTPS? Si alguna de estas es no, tienen A2.

A3
Injection — Inyección SQL / NoSQL

¿Usan métodos derivados de JPA o @Query con parámetros nombrados? JPA y MongoRepository ya protegen contra inyección. Si armaron queries concatenando strings, tienen A3.

A4
Insecure Design — Diseño inseguro

¿Existen endpoints que exponen más datos de los necesarios? Revisen que los ResponseDTO no incluyan campos sensibles (passwords, tokens internos, datos de otros usuarios).

A5
Security Misconfiguration — Mala configuración

¿El error 500 devuelve el stack trace completo? ¿Swagger está expuesto en producción sin autenticación? ¿Las credenciales están en el código fuente en Git?

A6
Vulnerable and Outdated Components

Ejecuten mvn dependency:check para ver si alguna dependencia tiene vulnerabilidades conocidas. Mantengan Spring Boot actualizado a la última versión estable.

A7
Identification and Authentication Failures

¿El endpoint de login tiene rate limiting? ¿Los tokens JWT tienen expiración? ¿Los passwords tienen validación de complejidad (@Size, @Pattern)? ¿Hay manejo correcto de tokens expirados (401, no 500)?

A8
Software and Data Integrity Failures

¿El JWT usa una firma con secret fuerte? ¿Verifican la firma en cada petición (lo hace jjwt automáticamente)? ¿Las dependencias de pom.xml vienen de repositorios confiables (Maven Central)?

A9
Security Logging and Monitoring Failures

¿Registran en logs los intentos de login fallidos? ¿Los accesos denegados (403)? ¿Los tokens inválidos? Sin estos logs, un ataque puede pasar desapercibido durante días.

A10
Server-Side Request Forgery (SSRF)

Si su API acepta URLs como parámetros de entrada (para consultar recursos externos), validen que apunten solo a dominios permitidos. Si no aceptan URLs en los inputs, no tienen este riesgo.

Paso 9 — Protección activa
CSRF · XSS · Clickjacking — cómo proteger su API

🎭 CSRF — Cross-Site Request Forgery

Un atacante hace que un usuario autenticado ejecute acciones sin saberlo (clic en link malicioso que llama a su API). Las APIs stateless con JWT no son vulnerables a CSRF clásico porque el token no se envía automáticamente — el cliente lo incluye explícitamente. Por eso deshabilitan CSRF en la configuración.

// En SecurityConfig — correcto para APIs con JWT
http.csrf(csrf -> csrf.disable());  // stateless + JWT = sin vulnerabilidad CSRF
💡
Si en el futuro agregan sesiones con cookies (no JWT), deberán reactivar CSRF con CsrfTokenRepository. Con JWT y SessionCreationPolicy.STATELESS, desactivarlo es la práctica correcta.

💉 XSS — Cross-Site Scripting

Un atacante inyecta scripts maliciosos que se ejecutan en el navegador de otro usuario. La defensa en Spring Boot son los headers HTTP de seguridad:

@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    return http
        .headers(headers -> headers
            .contentSecurityPolicy(csp -> csp
                .policyDirectives("default-src 'self'; script-src 'self'"))
            .frameOptions(frame -> frame.deny())        // bloquea iframes
            .xssProtection(xss -> xss.headerValue(      // activa filtro XSS del navegador
                XXssProtectionHeaderWriter.HeaderValue.ENABLED_MODE_BLOCK))
        )
        // ... resto de la config
        .build();
}

En el frontend React: nunca usen dangerouslySetInnerHTML con datos del usuario. React escapa automáticamente las variables en JSX — no salten esa protección.

🖱️ Clickjacking

Un atacante embebe su app en un iframe invisible para engañar a los usuarios a hacer clic en acciones no deseadas. El header X-Frame-Options: DENY lo previene — ya lo activan con frameOptions(frame -> frame.deny()) en la configuración anterior.

// Verificar que el header aparece en las respuestas:
// En Postman o curl, revisen los headers de respuesta:
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
X-XSS-Protection: 1; mode=block

Paso 10 — Verificación final
Prueben que todo funciona — checklist de seguridad
  • Login exitoso: POST a /api/v1/auth/login con credenciales válidas → devuelve 200 con token JWT
  • Login fallido: POST a /api/v1/auth/login con contraseña incorrecta → devuelve 401
  • Sin token: GET a un endpoint protegido sin Authorization header → devuelve 401
  • Token inválido: GET con Authorization: Bearer tokenbasura → devuelve 401
  • Token expirado: esperen a que expire el TTL y ejecuten → devuelve 401
  • Acceso denegado por rol: CLIENTE intenta POST a /platos → devuelve 403
  • Acceso permitido por rol: CHEF hace POST a /platos con token válido → devuelve 201
  • Swagger con autenticación: hagan clic en "Authorize" en Swagger UI → ingresan el token → ejecutan endpoint protegido → 200
  • Headers de seguridad: revisen en Postman los headers de respuesta — deben ver X-Frame-Options, X-Content-Type-Options
  • Password hasheado: consulten la BD directamente — el campo password debe verse como $2a$10$..., nunca en texto plano
  • CORS: si tienen frontend, prueben que React puede llamar a la API sin errores de CORS en la consola del navegador

Prueba de seguridad con MockMvc: agreguen una prueba unitaria que verifique que los endpoints protegidos devuelven 401/403 sin autenticación.
@SpringBootTest @AutoConfigureMockMvc
class SecurityTest {

    @Autowired private MockMvc mockMvc;

    @Test
    void crearPlato_sinToken_devuelve401() throws Exception {
        mockMvc.perform(post("/api/v1/platos")
                .contentType(MediaType.APPLICATION_JSON)
                .content("{\"nombre\":\"Bandeja\",\"precio\":28000}"))
                .andExpect(status().isUnauthorized());
    }

    @Test
    @WithMockUser(roles = "CLIENTE")
    void crearPlato_conRolCliente_devuelve403() throws Exception {
        mockMvc.perform(post("/api/v1/platos")
                .contentType(MediaType.APPLICATION_JSON)
                .content("{\"nombre\":\"Bandeja\",\"precio\":28000}"))
                .andExpect(status().isForbidden());
    }
}

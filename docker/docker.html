Paso 1 — Fundamentos
Imagen vs Contenedor — qué es Docker y por qué importa

📦 Imagen

Plantilla inmutable con el código, el runtime y las dependencias. Es el "molde". Se construye con docker build y se puede compartir en Docker Hub.

🏃 Contenedor

Instancia en ejecución de una imagen. Es el "objeto" creado del molde. Pueden correr muchos contenedores del mismo molde simultáneamente.

🗂️ Registry

Repositorio de imágenes. Docker Hub es el público. Su empresa o Azure Container Registry son privados. Se usa con docker pull y docker push.

Paso 2 — Empaquetar la API
Dockerfile — la receta para construir su imagen

El Dockerfile describe paso a paso cómo construir la imagen de su aplicación. Usan un build multietapa: la primera etapa compila el código con Maven, la segunda solo copia el JAR resultante — la imagen final no incluye Maven ni el código fuente.

# ─── Etapa 1: Compilar con Maven ───────────────────────────────
FROM maven:3.9-eclipse-temurin-21 AS builder
WORKDIR /app

# Copiar pom.xml primero para cachear dependencias
COPY pom.xml .
RUN mvn dependency:go-offline -q

# Copiar código fuente y compilar
COPY src ./src
RUN mvn clean package -DskipTests -q

# ─── Etapa 2: Imagen final ligera ──────────────────────────────
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app

# Copiar solo el JAR de la etapa anterior
COPY --from=builder /app/target/*.jar app.jar

# Variables de entorno con valores por defecto (se sobreescriben en Compose)
ENV SPRING_PROFILES_ACTIVE=docker
ENV SERVER_PORT=8080

EXPOSE 8080

# Arrancar la aplicación
ENTRYPOINT ["java", "-jar", "app.jar"]
⚠️
El Dockerfile va en la raíz del proyecto — al mismo nivel que pom.xml. No dentro de src/.

.dockerignore — qué no empaquetar

Creen un archivo .dockerignore en la raíz del proyecto para evitar copiar archivos innecesarios a la imagen:

application-docker.yml — configuración para el contenedor

# src/main/resources/application-docker.yml
spring:
  datasource:
    url: jdbc:postgresql://${DB_HOST:postgres}:${DB_PORT:5432}/${DB_NAME:restaurante}
    username: ${DB_USER:postgres}
    password: ${DB_PASSWORD:postgres}
  data:
    mongodb:
      uri: mongodb://${MONGO_HOST:mongo}:${MONGO_PORT:27017}/${MONGO_DB:restaurante}
  jpa:
    hibernate:
      ddl-auto: update
jwt:
  secret: ${JWT_SECRET}
  expiration-ms: 3600000
💡
Las variables de entorno entre ${...} con valor por defecto después de : permiten que la app arranque localmente sin variables de entorno, pero las sobreescriban en Docker Compose y en producción.

Paso 3 — Base de datos en contenedor
PostgreSQL · MongoDB en Docker — sin instalar nada en la máquina

Usen la imagen oficial de su BD. Con Docker ya no necesitan instalar PostgreSQL o MongoDB localmente — el contenedor lo provee. Los datos persisten en un volumen Docker.

🐘 PostgreSQL en Docker

# Correr PostgreSQL en un contenedor
$ docker run -d \
--name postgres-restaurante \
-e POSTGRES_DB=restaurante \
-e POSTGRES_USER=postgres \
-e POSTGRES_PASSWORD=postgres \
-p 5432:5432 \
-v postgres-data:/var/lib/postgresql/data \
postgres:16-alpine

Verificar: docker logs postgres-restaurante → deben ver "database system is ready to accept connections"

🍃 MongoDB en Docker

# Correr MongoDB en un contenedor
$ docker run -d \
--name mongo-restaurante \
-e MONGO_INITDB_ROOT_USERNAME=admin \
-e MONGO_INITDB_ROOT_PASSWORD=admin \
-e MONGO_INITDB_DATABASE=restaurante \
-p 27017:27017 \
-v mongo-data:/data/db \
mongo:7
💡
Los volúmenes (-v nombre:/ruta) son clave. Sin volumen, los datos desaparecen cuando el contenedor se elimina. El volumen persiste incluso si recrean el contenedor — los datos sobreviven.

Paso 4 — Orquestar todo junto
docker-compose.yml — API + BD en un solo comando

Docker Compose define todos los servicios de su stack en un archivo YAML. Un solo comando levanta la API, PostgreSQL, MongoDB y cualquier dependencia — con las redes y volúmenes configurados automáticamente.

# docker-compose.yml — en la raíz del proyecto
version: '3.9'

services:

  api:
    build: .                        # construye desde el Dockerfile local
    container_name: restaurante-api
    ports:
      - "8080:8080"
    environment:
      SPRING_PROFILES_ACTIVE: docker
      DB_HOST: postgres
      DB_PORT: 5432
      DB_NAME: restaurante
      DB_USER: postgres
      DB_PASSWORD: postgres
      MONGO_HOST: mongo
      MONGO_PORT: 27017
      MONGO_DB: restaurante
      JWT_SECRET: ${JWT_SECRET}   # viene del .env — no hardcodeado aquí
    depends_on:
      postgres:
        condition: service_healthy
      mongo:
        condition: service_started
    networks:
      - restaurante-net

  postgres:
    image: postgres:16-alpine
    container_name: restaurante-postgres
    environment:
      POSTGRES_DB: restaurante
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: postgres
    ports:
      - "5432:5432"
    volumes:
      - postgres-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 10s
      timeout: 5s
      retries: 5
    networks:
      - restaurante-net

  mongo:
    image: mongo:7
    container_name: restaurante-mongo
    environment:
      MONGO_INITDB_ROOT_USERNAME: admin
      MONGO_INITDB_ROOT_PASSWORD: admin
    ports:
      - "27017:27017"
    volumes:
      - mongo-data:/data/db
    networks:
      - restaurante-net

volumes:
  postgres-data:
  mongo-data:

networks:
  restaurante-net:
    driver: bridge

Paso 6 — Publicar la imagen
Subir a Docker Hub — compartir su imagen con el mundo
  1. Crear cuenta en Docker Hub
    Ir a hub.docker.com y crear cuenta gratuita. El nombre de usuario es su namespace — las imágenes se llaman usuario/nombre-imagen:tag.
  2. Iniciar sesión desde la terminal
$ docker login
# Ingresan usuario y contraseña de Docker Hub
# Login Succeeded
  1. Construir con el nombre correcto para Docker Hub
# Reemplazar "suusuario" con su nombre en Docker Hub
$ docker build -t suusuario/restaurante-api:1.0 .
$ docker build -t suusuario/restaurante-api:latest .
  1. Subir (push) la imagen a Docker Hub
$ docker push suusuario/restaurante-api:1.0
$ docker push suusuario/restaurante-api:latest
  1. Verificar que está en Docker Hub
    Entren a hub.docker.com/r/suusuario/restaurante-api — deben ver su imagen publicada. Prueben que funciona descargándola en otro directorio:
# Eliminar la imagen local para probar el pull
$ docker rmi suusuario/restaurante-api:1.0
$ docker run -d -p 8080:8080 suusuario/restaurante-api:1.0
# Docker descarga automáticamente desde Hub y corre el contenedor

Paso 7 — El siguiente nivel
Kubernetes — orquestación de contenedores en producción
☸️
Kubernetes (K8s) es para producción a escala. Mientras Docker Compose maneja múltiples servicios en una sola máquina, Kubernetes distribuye y orquesta contenedores a través de un clúster de máquinas, con autoescalado, auto-recuperación y despliegues sin downtime. Esta sección es una introducción — no necesitan implementarlo en su proyecto del curso, pero sí entender la arquitectura.

🏗️ Pod

La unidad mínima en K8s. Un Pod contiene uno o más contenedores que comparten red y almacenamiento. En la mayoría de casos, un Pod = un contenedor.

📦 Deployment

Define cuántas réplicas (Pods) de su app deben correr. K8s las mantiene activas — si un Pod falla, lo recrea automáticamente.

🌐 Service

Expone un Deployment con una IP estable. Los Pods pueden ser eliminados y recreados con nuevas IPs, pero el Service siempre apunta a los Pods activos.

⚙️ ConfigMap / Secret

Equivalente a las variables de entorno del docker-compose. ConfigMap para config no sensible, Secret para passwords y tokens — siempre encriptados.

Ejemplo de Deployment para su API

# k8s/deployment.yml — para referencia, no necesitan aplicarlo ahora
apiVersion: apps/v1
kind: Deployment
metadata:
  name: restaurante-api
spec:
  replicas: 2                        # dos instancias corriendo siempre
  selector:
    matchLabels:
      app: restaurante-api
  template:
    metadata:
      labels:
        app: restaurante-api
    spec:
      containers:
        - name: api
          image: suusuario/restaurante-api:latest
          ports:
            - containerPort: 8080
          env:
            - name: JWT_SECRET
              valueFrom:
                secretKeyRef:        # viene de un K8s Secret
                  name: restaurante-secrets
                  key: jwt-secret
          readinessProbe:            # K8s espera a que la app esté lista
            httpGet:
              path: /actuator/health
              port: 8080
            initialDelaySeconds: 30
---
apiVersion: v1
kind: Service
metadata:
  name: restaurante-api-svc
spec:
  selector:
    app: restaurante-api
  ports:
    - port: 80
      targetPort: 8080
  type: LoadBalancer               # expone con IP pública en la nube
💡
Para experimentar con K8s localmente: Docker Desktop incluye un clúster de K8s de un nodo que pueden activar en Settings → Kubernetes → Enable Kubernetes. También pueden usar minikube. En el proyecto del curso, su despliegue será en Azure — el CI/CD del siguiente sprint configura eso.

Paso 8 — Todo funcionando
Verifiquen que el stack completo corre en Docker
  1. Levantar el stack completo
$ docker compose up --build -d
# Debe ver: Creating restaurante-postgres, restaurante-mongo, restaurante-api
  1. Verificar que todos los servicios están corriendo
$ docker compose ps
# Todos deben mostrar "running" o "healthy"
  1. Revisar los logs de la API
$ docker compose logs api
# Deben ver "Started RestauranteApplication" sin errores de conexión a BD
  • docker compose ps muestra los tres servicios en estado running o healthy
  • Swagger accesible en http://localhost:8080/swagger-ui/index.html desde el navegador
  • Ejecutar un POST desde Swagger y ver que los datos persisten en la BD (usar pgAdmin o MongoDB Compass apuntando al puerto del contenedor)
  • Reiniciar el contenedor de la API (docker compose restart api) y verificar que los datos siguen en la BD
  • Link a la imagen en Docker Hub accesible públicamente

CI/CD con GitHub Actions

El código que no se despliega automáticamente se despliega tarde, con errores o no se despliega. CI/CD convierte cada push en un proceso verificado: pruebas, build, imagen Docker y despliegue en Azure — sin intervención manual.

Paso 1 — Fundamentos
CI/CD — qué es y por qué su API lo necesita

🔧 CI — Integración Continua

Cada vez que hacen push a GitHub, se ejecutan automáticamente las pruebas y se construye la imagen Docker. Si algo falla, el equipo sabe de inmediato — antes de que llegue a producción.

🚀 CD — Despliegue Continuo

Si el pipeline de CI pasa, el código se despliega automáticamente al ambiente correspondiente (QA o PROD) en Azure. Sin copiar archivos manualmente, sin SSH, sin errores humanos.

💡
Los workflows de GitHub Actions van en .github/workflows/ — GitHub los detecta automáticamente. Cada archivo .yml es un pipeline independiente con sus propias reglas de disparo.

Dos ambientes — QA y PROD

AmbienteCuándo se activaPropósitoAprobación
🧪 QA Push a rama main o develop Validar que el código funciona después de merges. El equipo prueba aquí. Automática — sin aprobación manual
🚀 PROD Tag de versión v*.*.* o aprobación manual API que usan los usuarios reales. Solo llega código validado en QA. Requiere aprobación manual en GitHub

Paso 3 — Configuración segura
Secrets — variables sensibles en GitHub, no en el código

Las credenciales de la BD, el JWT secret, las claves de Azure y el token de Docker Hub nunca van en el código. GitHub guarda estos valores encriptados como Secrets y los inyecta en el pipeline cuando se ejecuta.

  1. Ir a Settings → Secrets and variables → Actions en su repositorio
    Cada repositorio tiene su propia sección de secrets. Los Secrets de Organization aplican a todos los repositorios de la organización.
  2. Crear los siguientes secrets
SecretValorPara qué sirve
DOCKERHUB_USERNAMESu usuario de Docker HubLogin para hacer push de la imagen
DOCKERHUB_TOKENToken de acceso de Docker Hub (no el password)Autenticación segura sin exponer el password
AZURE_CREDENTIALSJSON de credenciales del Service Principal de AzurePermite a GitHub Actions desplegar en Azure
JWT_SECRET_QASecret JWT para ambiente QADistinto del de PROD — cada ambiente tiene el suyo
JWT_SECRET_PRODSecret JWT para ambiente PRODMás seguro, rotado periódicamente
DB_PASSWORD_QAPassword de la BD en Azure QACredencial de la BD de QA
DB_PASSWORD_PRODPassword de la BD en Azure PRODCredencial de la BD de producción
AZURE_WEBAPP_NAME_QANombre del App Service de QA en AzureA dónde desplegar en QA
AZURE_WEBAPP_NAME_PRODNombre del App Service de PROD en AzureA dónde desplegar en PROD
🚨
Nunca usen el mismo JWT secret ni las mismas credenciales de BD en QA y PROD. Si QA se compromete, PROD sigue siendo seguro. Cada ambiente es independiente.

Crear el token de Docker Hub

  1. Ir a hub.docker.com → Account Settings → Security → New Access Token
    Nombre: github-actions. Permisos: Read & Write. Copiar el token inmediatamente — solo se muestra una vez.
  2. Guardarlo como secret DOCKERHUB_TOKEN en GitHub
    Nunca en el código, nunca en un archivo que se vaya a commitear.

Paso 4 — Integración continua
Pipeline QA — tests + build + despliegue automático
# .github/workflows/ci-qa.yml
name: CI — Build · Test · Deploy QA

on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main ]

env:
  IMAGE_NAME: ${{ secrets.DOCKERHUB_USERNAME }}/restaurante-api

jobs:

  test:
    name: 🧪 Pruebas
    runs-on: ubuntu-latest
    steps:
      - name: Checkout código
        uses: actions/checkout@v4

      - name: Configurar Java 21
        uses: actions/setup-java@v4
        with:
          java-version: '21'
          distribution: 'temurin'

      - name: Cache Maven
        uses: actions/cache@v4
        with:
          path: ~/.m2
          key: ${{ runner.os }}-maven-${{ hashFiles('**/pom.xml') }}

      - name: Ejecutar pruebas
        run: mvn test --no-transfer-progress

      - name: Publicar reporte de cobertura
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: coverage-report
          path: target/site/jacoco/

  build-and-push:
    name: 🐳 Build imagen Docker
    needs: test                     # solo si los tests pasan
    runs-on: ubuntu-latest
    outputs:
      image-tag: ${{ steps.meta.outputs.version }}
    steps:
      - uses: actions/checkout@v4

      - name: Login a Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Metadata de la imagen
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.IMAGE_NAME }}
          tags: |
            type=sha,prefix=qa-        # tag: qa-abc1234
            type=raw,value=qa-latest

      - name: Build y push
        uses: docker/build-push-action@v5
        with:
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

  deploy-qa:
    name: 🚀 Desplegar a QA
    needs: build-and-push
    runs-on: ubuntu-latest
    environment: qa                 # ambiente configurado en GitHub
    steps:
      - name: Login a Azure
        uses: azure/login@v1
        with:
          creds: ${{ secrets.AZURE_CREDENTIALS }}

      - name: Desplegar en Azure Web App (QA)
        uses: azure/webapps-deploy@v3
        with:
          app-name: ${{ secrets.AZURE_WEBAPP_NAME_QA }}
          images: ${{ env.IMAGE_NAME }}:qa-latest

      - name: Configurar variables de entorno en Azure QA
        uses: azure/appservice-settings@v1
        with:
          app-name: ${{ secrets.AZURE_WEBAPP_NAME_QA }}
          app-settings-json: |
            [
              {"name": "SPRING_PROFILES_ACTIVE", "value": "docker"},
              {"name": "JWT_SECRET", "value": "${{ secrets.JWT_SECRET_QA }}"},
              {"name": "DB_PASSWORD", "value": "${{ secrets.DB_PASSWORD_QA }}"}
            ]

Paso 5 — Despliegue controlado
Pipeline PROD — aprobación manual + despliegue
🌱
El pipeline de PROD requiere aprobación manual. Ningún push va directamente a producción sin que alguien del equipo revise y apruebe en GitHub. Esto es la línea de defensa entre "funciona en QA" y "está en producción".

🔧 Configurar el environment de producción en GitHub

  1. Ir a Settings → Environments → New environment
    Nombre: production. Activar "Required reviewers" y agregar a los integrantes del equipo. Con esto, el workflow de PROD se pausa hasta que alguien apruebe.
  2. Agregar los secrets específicos de PROD
    JWT_SECRET_PROD, DB_PASSWORD_PROD, AZURE_WEBAPP_NAME_PROD — distintos de los de QA.
# .github/workflows/ci-prod.yml
name: CD — Deploy PROD

on:
  push:
    tags:
      - 'v*.*.*'        # se activa al crear un tag: git tag v1.0.0 && git push --tags

env:
  IMAGE_NAME: ${{ secrets.DOCKERHUB_USERNAME }}/restaurante-api

jobs:

  build-prod:
    name: 🐳 Build imagen PROD
    runs-on: ubuntu-latest
    outputs:
      version: ${{ steps.meta.outputs.version }}
    steps:
      - uses: actions/checkout@v4

      - name: Login a Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Metadata con el tag de versión
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.IMAGE_NAME }}
          tags: |
            type=semver,pattern={{version}}   # v1.0.0
            type=raw,value=latest             # latest actualizado

      - name: Build y push imagen de producción
        uses: docker/build-push-action@v5
        with:
          push: true
          tags: ${{ steps.meta.outputs.tags }}

  deploy-prod:
    name: 🚀 Desplegar a PROD
    needs: build-prod
    runs-on: ubuntu-latest
    environment: production         # ← pausa aquí hasta aprobación manual
    steps:
      - name: Login a Azure
        uses: azure/login@v1
        with:
          creds: ${{ secrets.AZURE_CREDENTIALS }}

      - name: Desplegar en Azure Web App (PROD)
        uses: azure/webapps-deploy@v3
        with:
          app-name: ${{ secrets.AZURE_WEBAPP_NAME_PROD }}
          images: ${{ env.IMAGE_NAME }}:${{ needs.build-prod.outputs.version }}

      - name: Configurar variables PROD
        uses: azure/appservice-settings@v1
        with:
          app-name: ${{ secrets.AZURE_WEBAPP_NAME_PROD }}
          app-settings-json: |
            [
              {"name": "SPRING_PROFILES_ACTIVE", "value": "docker"},
              {"name": "JWT_SECRET", "value": "${{ secrets.JWT_SECRET_PROD }}"},
              {"name": "DB_PASSWORD", "value": "${{ secrets.DB_PASSWORD_PROD }}"}
            ]

  notify:
    name: 📣 Notificación
    needs: deploy-prod
    runs-on: ubuntu-latest
    steps:
      - name: Resumen del despliegue
        run: |
          echo "✅ PROD desplegado exitosamente"
          echo "Versión: ${{ github.ref_name }}"
          echo "URL: https://${{ secrets.AZURE_WEBAPP_NAME_PROD }}.azurewebsites.net"

Paso 6 — Base de datos en la nube
Crear la BD en Azure — un ambiente por vez
☁️
Azure for Students da $100 USD de crédito. Verifiquen que tienen acceso en azure.microsoft.com/free/students. Con eso cubren una BD pequeña y un App Service para la duración del proyecto.

🐘 Azure Database for PostgreSQL

  1. Crear el servidor en el portal de Azure
    Buscar "Azure Database for PostgreSQL" → Flexible server. Tier: Burstable B1ms (el más económico). Región: East US o la más cercana. Crear dos instancias: una para QA, una para PROD — con nombres distintos.
  2. Configurar el firewall
    En "Networking" del servidor → Agregar regla: permitir IPs de GitHub Actions. GitHub publica sus rangos de IPs en api.github.com/meta. También pueden activar "Allow access to Azure services" temporalmente.
  3. Obtener la cadena de conexión
    En el portal: Settings → Connect → Java. Tendrán algo como: jdbc:postgresql://servidor-qa.postgres.database.azure.com:5432/restaurante?sslmode=require
  4. Guardar el host y password como Secrets en GitHub
    DB_HOST_QA, DB_HOST_PROD, DB_PASSWORD_QA, DB_PASSWORD_PROD

🍃 Azure Cosmos DB for MongoDB

  1. Buscar "Azure Cosmos DB" → Create → Azure Cosmos DB for MongoDB
    API: MongoDB. Tier: Free tier (gratis, 400 RU/s y 5 GB). Una instancia por ambiente.
  2. Obtener el connection string
    Settings → Connection String → PRIMARY CONNECTION STRING. Tiene el formato: mongodb://cuenta:password@cuenta.mongo.cosmos.azure.com:10255/?ssl=true&...

Paso 7 — Su API en línea
Azure App Service — correr su contenedor en la nube
  1. Crear el App Service en Azure
    Buscar "App Service" → Create. Publish: Container. OS: Linux. Crear dos: uno para QA (restaurante-qa), uno para PROD (restaurante-prod).
  2. Configurar el contenedor en el App Service
    Settings → Configuration → Container settings → Docker Hub → imagen: suusuario/restaurante-api:qa-latest. Continuous deployment: ON (Azure verifica cada 5 min si hay nueva imagen).
  3. Crear el Service Principal para GitHub Actions
    En Azure Cloud Shell o desde la terminal con Azure CLI:
# Instalar Azure CLI si no lo tienen: https://docs.microsoft.com/cli/azure/install-azure-cli
az login

# Obtener el ID de la suscripción
az account show --query id -o tsv

# Crear el Service Principal — guardar el JSON completo como AZURE_CREDENTIALS en GitHub
az ad sp create-for-rbac \
  --name "github-actions-restaurante" \
  --role contributor \
  --scopes /subscriptions/{subscription-id}/resourceGroups/{resource-group} \
  --json-auth
  1. Verificar la URL de su API en Azure
    En el portal: App Service → Overview → URL. Será algo como https://restaurante-qa.azurewebsites.net. Prueben el Swagger: https://restaurante-qa.azurewebsites.net/swagger-ui/index.html
✅
El URL de su API desplegada va en el README — QA y PROD separados. Es la evidencia principal de que el CI/CD funciona.

Paso 8 — Documentación visual
Diagrama de despliegue — cómo está desplegado su sistema
⚠️
El diagrama de despliegue lo hacen manual — en draw.io, Lucidchart o Miro, con el código de colores de su equipo. No Mermaid ni autogenerado. Este diagrama muestra la arquitectura real de su sistema en producción.

Qué debe mostrar su diagrama de despliegue

🌐 Nodos (como cubos UML)

Desarrollador → GitHub → GitHub Actions → Azure App Service QA → Azure App Service PROD. Cada nodo es un cuadrado con el nombre del servicio.

📦 Artefactos

Imagen Docker en Docker Hub (entre GitHub Actions y los App Services). Archivos de workflow (.yml) en el nodo de GitHub Actions.

🗄️ Almacenamiento

Azure Database for PostgreSQL (QA) conectado al App Service QA. Azure Database for PostgreSQL (PROD) conectado al App Service PROD. Lo mismo para MongoDB si aplica.

↔️ Comunicaciones

Líneas sólidas entre nodos con el protocolo: HTTPS entre cliente y API, JDBC/MongoDB entre API y BD, CI/CD entre GitHub Actions y Azure.

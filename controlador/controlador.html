🔑 Las 4 reglas que no se negocian

✅
El Mapper vive en el Controller — no en el Service. El Service recibe y devuelve objetos de dominio, nunca DTOs.
✅
El Service devuelve objetos de dominio — nunca un ResponseDTO. La conversión a DTO la hace el Controller justo antes de responder.
✅
El Controller no tiene lógica de negocio — solo recibe, traduce, delega y responde.
✅
Las validaciones de input van en el DTO con Bean Validation. Las validaciones de negocio van en el Service con excepciones propias.
⚠️
¿Por qué el Mapper NO va en el Service? Si el Service devuelve un ResponseDTO, está acoplado a la capa de presentación. El día que necesites otro formato de respuesta (v2 del API, WebSocket, exportación a PDF) tienes que tocar el Service — y el Service es donde vive tu lógica de negocio. El Mapper en el Controller mantiene esas dos responsabilidades separadas.

Paso 01
Las clases de dominio
El dominio es el núcleo. Todo lo demás (DTOs, Mappers, Services) orbita alrededor de estas clases. Si el dominio está mal modelado, todo lo demás también lo está.
🏗️
🏗️
Paso 01 — model/domain/
Clases de dominio con Lombok

Las clases de dominio representan los conceptos del negocio — sin anotaciones de Spring, sin DTOs, sin nada que las acople a la infraestructura. Son Java puro con Lombok para no escribir getters, setters y constructores a mano.

// model/domain/Plato.java
@Data                  // genera getters, setters, equals, hashCode, toString
@NoArgsConstructor    // constructor vacío (necesario para deserialización)
@AllArgsConstructor   // constructor con todos los campos
@Builder              // patrón Builder: Plato.builder().nombre("X").build()
public class Plato {

    private Long    id;
    private String  nombre;
    private Double  precio;
    private String  categoria;
    private Boolean disponible;
    private String  descripcion;

    // ✅ Comportamiento de negocio propio del objeto
    // El dominio sabe qué puede hacer — sin depender de estado externo
    public boolean estaDisponible() {
        return Boolean.TRUE.equals(disponible);
    }

    // Activa/desactiva sin que el Service tenga que tocar el campo directamente
    public void activar()   { this.disponible = true;  }
    public void desactivar(){ this.disponible = false; }
}

// ❌ Lo que NO va en el dominio:
//    public boolean esValido() { return nombre != null && precio > 0; }
//    → Eso ya lo garantiza el @NotBlank y @Positive del RequestDTO.
//    Si el objeto existe, es porque el input ya fue validado.
//    Duplicarlo aquí solo crea dos fuentes de verdad que pueden desincronizarse.

// model/domain/EstadoPedido.java — Enum con comportamiento de negocio
public enum EstadoPedido {
    RECIBIDO, EN_PREPARACION, LISTO, ENTREGADO, CANCELADO;

    // ✅ La regla de transición vive en el Enum — es parte del dominio
    // Nadie más la conoce: ni el Service, ni el Validator, ni el Controller
    public boolean puedeTransicionarA(EstadoPedido siguiente) {
        return switch (this) {
            case RECIBIDO       -> siguiente == EN_PREPARACION || siguiente == CANCELADO;
            case EN_PREPARACION -> siguiente == LISTO;
            case LISTO          -> siguiente == ENTREGADO;
            default             -> false;
        };
    }

    public boolean esCancelable() {
        return this == RECIBIDO;
    }
}
🌿
¿Qué SÍ va como método en el dominio?
Comportamiento que el objeto sabe ejecutar sobre su propio estado interno, sin depender de nada externo: estaDisponible(), activar(), puedeTransicionarA(), esCancelable(), estaVigente() en Reserva, subtotal() en ItemPedido.

¿Qué NO va en el dominio?
Validaciones de formato que ya cubre el DTO (esValido(), precioEsPositivo()), ni reglas que cruzan objetos ("¿el nombre ya existe?" requiere consultar la colección → eso es el Validator).
🌿
Estructura de paquetes recomendada
model/domain/ → clases de negocio + enums
model/dto/request/ → lo que entra al API
model/dto/response/ → lo que sale del API
mapper/ → conversión entre capas
service/ → interfaces (contratos)
service/impl/ → implementaciones
controller/ → endpoints REST
exception/ → excepciones + handler
validator/ → validadores de negocio (opcional)
Paso 02
Los DTOs — lo que entra y lo que sale
Un DTO por funcionalidad, no uno para todo. El Request valida el input. El Response controla exactamente qué le muestras al cliente — nunca el objeto de dominio completo.
📦
📦
Paso 02 — model/dto/
DTOs de Request y Response
💡
Antes de crear un DTO hazte estas preguntas: ¿Requiere datos de entrada? ¿Hay campos opcionales? ¿Qué devuelve en caso de éxito? ¿Qué devuelve en caso de error? — La respuesta determina cuántos DTOs necesitas por endpoint.

📥 RequestDTO — lo que entra

// model/dto/request/PlatoRequestDTO.java
@Data
@NoArgsConstructor
@AllArgsConstructor
public class PlatoRequestDTO {

    @NotBlank(message = "El nombre es obligatorio")
    @Size(max = 100, message = "Máximo 100 caracteres")
    private String nombre;

    @NotNull(message = "El precio es obligatorio")
    @Positive(message = "El precio debe ser mayor a 0")
    private Double precio;

    @NotBlank(message = "La categoría es obligatoria")
    private String categoria;

    // Campo opcional — sin @NotNull
    private String descripcion;
}

📤 ResponseDTO — lo que sale

// model/dto/response/PlatoResponseDTO.java
@Data
@NoArgsConstructor
@AllArgsConstructor
@Builder
public class PlatoResponseDTO {

    private Long    id;
    private String  nombre;
    private Double  precio;
    private String  categoria;
    private Boolean disponible;

    // ✅ Solo los campos que el cliente necesita ver
    // ❌ NO expongas campos internos del dominio
    // ❌ NO pongas la clase de dominio directamente
}
⚠️
¿Un DTO por endpoint o uno compartido? Si dos endpoints reciben los mismos campos → comparten el RequestDTO. Si uno recibe menos → crea uno específico. No hagas un RequestDTO con 15 campos opcionales para cubrirlo todo — eso rompe el principio de responsabilidad única y hace inútil la validación.

⏸ Pausa rápida DTOs — antes de seguir
¿Por qué el Service no devuelve el ResponseDTO directamente?
Porque el Service no debería saber nada de la capa de presentación. Si mañana el ResponseDTO cambia (versión v2 del API), tendrías que tocar el Service — y el Service es donde vive la lógica de negocio. La conversión la hace el Controller con el Mapper.
¿Puede el RequestDTO tener campos opcionales?
Sí — simplemente no les pones @NotNull ni @NotBlank. En el Service validas si el valor fue enviado antes de usarlo.

el traductor entre capas

Paso 03 — mapper/
Mapper — traducción entre DTOs y dominio
🚨
Regla fundamental: El Mapper se inyecta en el Controller. Nunca en el Service. El Service recibe objetos de dominio y devuelve objetos de dominio. El Controller usa el Mapper para traducir antes de llamar al Service y después de recibir la respuesta.

Dependencia en pom.xml — MapStruct + Lombok juntos

<!-- MapStruct -->
<dependency>
    <groupId>org.mapstruct</groupId>
    <artifactId>mapstruct</artifactId>
    <version>1.5.5.Final</version>
</dependency>

<!-- Plugin del compilador — Lombok DEBE ir antes que MapStruct -->
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <configuration>
        <annotationProcessorPaths>
            <path>
                <groupId>org.projectlombok</groupId>
                <artifactId>lombok</artifactId>
            </path>
            <path>
                <groupId>org.mapstruct</groupId>
                <artifactId>mapstruct-processor</artifactId>
                <version>1.5.5.Final</version>
            </path>
        </annotationProcessorPaths>
    </configuration>
</plugin>
⚠️
Lombok antes que MapStruct en el pom — siempre. MapStruct genera código a partir de los getters/setters de Lombok. Si Lombok no procesó primero, MapStruct no encuentra los métodos y falla con errores crípticos en compilación.

El Mapper con MapStruct — interfaz + @Mapping

MapStruct genera en tiempo de compilación la implementación completa de la interfaz. Tú solo declaras los métodos y anotas los campos que no se pueden mapear automáticamente. Si un campo de origen y destino tienen el mismo nombre y tipo, MapStruct lo mapea solo — sin escribir nada.

// mapper/PlatoMapper.java
@Mapper(componentModel = "spring")
// componentModel = "spring" → MapStruct genera un @Component
// que Spring gestiona — se inyecta normalmente con @Autowired o constructor
public interface PlatoMapper {

    // ── MapperIn: RequestDTO → Dominio ──────────────────────────────────
    // Los campos con el mismo nombre (nombre, precio, categoria, descripcion)
    // se mapean automáticamente. Solo anotamos los que difieren o necesitan
    // un valor especial.
    @Mapping(target = "id",         ignore = true)   // el id lo asigna el sistema
    @Mapping(target = "disponible", constant = "true") // todo plato nuevo empieza disponible
    Plato toDomain(PlatoRequestDTO dto);

    // ── MapperOut: Dominio → ResponseDTO ────────────────────────────────
    // Todos los campos coinciden — MapStruct los mapea sin anotaciones.
    PlatoResponseDTO toResponse(Plato plato);

    // ── Lista: MapStruct genera el bucle automáticamente ────────────────
    List<PlatoResponseDTO> toResponseList(List<Plato> platos);
}

Los @Mapping que más vas a necesitar

CasoAnotaciónCuándo usarlo

🌿
Lo que MapStruct genera por ti — después de compilar con mvn compile, en target/generated-sources/ aparece PlatoMapperImpl.java. Es Java puro: un for-each para las listas, asignaciones campo a campo, null-checks. Puedes abrirlo y leerlo si algo no funciona como esperas — es el primer lugar donde buscar cuando el mapeo da resultados raros.
✅ ¿Compiló MapStruct? — verificación rápida
  • Ejecuta mvn compile
  • Busca en target/generated-sources/annotations/ los archivos *MapperImpl.java
  • Si no aparecen → revisa el orden de Lombok/MapStruct en el plugin del compilador
  • Si aparecen pero hay errores de compilación → revisa que todos los campos del target estén mapeados o ignorados explícitamente

Paso 04 — service/ + service/impl/
Interfaz del Service e Implementación

Primero — la interfaz (el contrato)

// service/IPlatoService.java
public interface IPlatoService {

    // ✅ Métodos reciben y devuelven objetos de DOMINIO — nunca DTOs
    List<Plato>  obtenerTodos();
    List<Plato>  obtenerDisponibles();
    Plato        obtenerPorId(Long id);
    Plato        crear(Plato plato);
    Plato        actualizar(Long id, Plato plato);
    Plato        cambiarDisponibilidad(Long id, boolean disponible);
    void         eliminar(Long id);
}

La implementación — todo con Streams

// service/impl/PlatoServiceImpl.java
@Service
@Slf4j
@RequiredArgsConstructor
public class PlatoServiceImpl implements IPlatoService {

    private final Map<Long, Plato> platos  = new ConcurrentHashMap<>();
    private final AtomicLong          contador = new AtomicLong(1);
    private final IPlatoValidator      validator;

    @Override
    public List<Plato> obtenerTodos() {
        log.info("Obteniendo todos los platos. Total: {}", platos.size());
        return platos.values().stream()
                .toList();
    }

    @Override
    public List<Plato> obtenerDisponibles() {
        return platos.values().stream()
                .filter(Plato::estaDisponible)
                .toList();
    }

    @Override
    public List<Plato> obtenerPorCategoria(String categoria) {
        return platos.values().stream()
                .filter(p -> p.getCategoria().equalsIgnoreCase(categoria))
                .toList();
    }

    @Override
    public Plato obtenerPorId(Long id) {
        return platos.values().stream()
                .filter(p -> p.getId().equals(id))
                .findFirst()
                .orElseThrow(() -> {
                    log.warn("Plato no encontrado: id={}", id);
                    return new RecursoNoEncontradoException("Plato", id);
                });
    }

    @Override
    public Plato crear(Plato plato) {
        validator.validarNombreUnico(plato.getNombre(), platos.values());
        plato.setId(contador.getAndIncrement());
        platos.put(plato.getId(), plato);
        log.info("Plato creado: id={}, nombre={}", plato.getId(), plato.getNombre());
        return plato;
    }

    @Override
    public Plato actualizar(Long id, Plato nuevosDatos) {
        Plato existente = obtenerPorId(id);  // lanza 404 si no existe
        validator.validarNombreUnico(nuevosDatos.getNombre(),
            platos.values().stream()
                    .filter(p -> !p.getId().equals(id))  // excluye el propio plato
                    .toList());
        existente.setNombre(nuevosDatos.getNombre());
        existente.setPrecio(nuevosDatos.getPrecio());
        existente.setCategoria(nuevosDatos.getCategoria());
        existente.setDescripcion(nuevosDatos.getDescripcion());
        log.info("Plato actualizado: id={}", id);
        return existente;
    }

    @Override
    public Plato cambiarDisponibilidad(Long id, boolean disponible) {
        Plato plato = obtenerPorId(id);
        if (disponible) plato.activar(); else plato.desactivar();
        log.info("Plato id={} → disponible={}", id, disponible);
        return plato;
    }

    @Override
    public void eliminar(Long id) {
        obtenerPorId(id);  // lanza 404 si no existe
        // En versiones futuras: validator.validarSinPedidosActivos(id, pedidosActivos);
        platos.remove(id);
        log.info("Plato eliminado: id={}", id);
    }
}

⚠️
Un Service puede depender de otro Service — siempre via interfaz. Si el día de mañana PedidoServiceImpl necesita verificar que un plato existe, inyecta IPlatoService — nunca la implementación concreta. Cuidado con dependencias circulares: si A depende de B y B depende de A, Spring no puede resolver la inyección.

Paso 05 — validator/ + @Valid en Controller
Validaciones de input y de negocio
✅ Validación de INPUT — en el DTO

¿El formato es correcto? ¿El campo está presente? ¿El número está en rango? → Bean Validation con anotaciones.

  • @NotBlank, @NotNull, @NotEmpty
  • @Positive, @Min, @Max
  • @Size, @Email, @Pattern
  • Activada con @Valid en el Controller
⚙️ Validación de NEGOCIO — en el Service

¿Cumple la regla del dominio? ¿El plato ya existe? ¿El pedido está en estado modificable? → Excepciones propias tipadas.

  • ¿El nombre ya existe? → ConflictoException
  • ¿El estado permite la transición? → EstadoInvalidoException
  • ¿La mesa tiene cuenta abierta? → ReglaDeNegocioException
  • Puede delegarse a un Validator (SRP)

Validators como @Component — cada dominio tiene el suyo

El mismo patrón del Service aplica al Validator: interfaz que define el contrato, @Component que lo implementa. Cada Validator valida solo las reglas de su propio dominio. PlatoValidator valida reglas de Plato. Cuando implementes Pedido, crearás PedidoValidator para sus propias reglas. Nunca un Validator valida reglas de otro dominio.

// validator/IPlatoValidator.java — solo reglas del dominio Plato
public interface IPlatoValidator {
    void validarNombreUnico(String nombre, Collection<Plato> platosExistentes);
    void validarSinPedidosActivos(Long idPlato, Collection<Pedido> pedidosActivos);
}

    

    💡
    
¿Un Validator por dominio o uno transversal? La regla es simple: si la validación solo tiene sentido para Plato → va en PlatoValidator. Si la misma lógica la necesitan Pedido y Mesa → va en un ValidadorComun o en una Utility. Nunca copies código de validación — si lo vas a pegar en dos lugares, extráelo.

  


  

    

      ⏸ Pausa rápida
      Validaciones — ¿dónde va cada una?
    

    
¿El @Valid va en el Controller o en el Service?

    
En el Controller, en el parámetro del método: @RequestBody @Valid PlatoRequestDTO dto. Si @Valid no está, Bean Validation no se activa y el request pasa con datos inválidos al Service.

    
¿Dónde va "verificar que el nombre del plato no esté duplicado"?

    
En el Validator inyectado en el Service. Es una regla de negocio — requiere consultar el estado actual del sistema. No es una validación de formato del input.

    
¿Por qué el Validator usa una interfaz si solo hay una implementación?

    
Para poder mockearlo en las pruebas unitarias del Service. Con @Mock IPlatoValidator validator puedes controlar exactamente qué lanza en cada escenario, sin necesidad de que el Validator real ejecute toda su lógica.

Paso 05-B — util/
Utilidades — lógica compartida entre dominios

Las utilidades son clases de métodos estáticos (o @Component cuando necesitan dependencias) que contienen lógica genérica que no pertenece a ningún dominio en particular pero que varios componentes necesitan. La regla: si lo vas a escribir en dos lugares, crea una utility.

⚠️
¿Cuándo es una Utility y cuándo es un Validator? Si la lógica valida una regla de negocio y lanza excepción → es un Validator. Si la lógica transforma, calcula o formatea datos sin lanzar excepciones → es una Utility. Un Validator puede usar una Utility internamente.

Utility de fechas — útil para Reserva, Parqueadero, Pedido

// util/FechaUtils.java
public final class FechaUtils {

    private FechaUtils() {}  // evita instanciación — solo métodos estáticos

    private static final DateTimeFormatter FORMATO_DISPLAY =
            DateTimeFormatter.ofPattern("dd/MM/yyyy HH:mm");

    private static final DateTimeFormatter FORMATO_CORTO =
            DateTimeFormatter.ofPattern("dd/MM/yyyy");

    // Formatea un LocalDateTime para mostrarlo al cliente
    public static String formatearFecha(LocalDateTime fecha) {
        if (fecha == null) return "Sin fecha";
        return fecha.format(FORMATO_DISPLAY);
    }

    // Calcula minutos transcurridos desde una fecha hasta ahora
    public static long minutosDesde(LocalDateTime desde) {
        return ChronoUnit.MINUTES.between(desde, LocalDateTime.now());
    }

    // Verifica si una fecha está dentro del rango permitido para reservas
    public static boolean esFechaFutura(LocalDateTime fecha) {
        return fecha != null && fecha.isAfter(LocalDateTime.now());
    }

    // Verifica solapamiento de reservas: ¿dos reservas chocan en horario?
    public static boolean seSolapan(LocalDateTime inicio1, LocalDateTime fin1,
                                      LocalDateTime inicio2, LocalDateTime fin2) {
        return inicio1.isBefore(fin2) && fin1.isAfter(inicio2);
    }
}

Utility de cálculos — útil para Parqueadero, Cuenta, Pedido

// util/CalculoUtils.java
public final class CalculoUtils {

    private CalculoUtils() {}

    // Redondea a 2 decimales — evita problemas de punto flotante
    public static double redondear(double valor) {
        return Math.round(valor * 100.0) / 100.0;
    }

    // Cobra por minutos — útil para Parqueadero
    public static double calcularCobroPorMinutos(LocalDateTime entrada,
                                                   LocalDateTime salida,
                                                   double tarifaPorMinuto) {
        long minutos = ChronoUnit.MINUTES.between(entrada, salida);
        return redondear(minutos * tarifaPorMinuto);
    }

    // Aplica un porcentaje de descuento — útil para Cuenta o Reserva
    public static double aplicarDescuento(double total, double porcentaje) {
        return redondear(total * (1 - porcentaje / 100));
    }
}

Utility de Strings — normalización y limpieza

// util/TextoUtils.java
public final class TextoUtils {

    private TextoUtils() {}

    // Normaliza un nombre: quita espacios extra, primera letra mayúscula
    public static String normalizarNombre(String nombre) {
        if (nombre == null) return null;
        String limpio = nombre.strip().replaceAll("\\s+", " ");
        return limpio.substring(0, 1).toUpperCase()
             + limpio.substring(1).toLowerCase();
    }

    // Compara dos strings ignorando mayúsculas y espacios
    public static boolean sonIgualesNormalizados(String a, String b) {
        if (a == null || b == null) return false;
        return a.strip().equalsIgnoreCase(b.strip());
    }

    // Genera un código de referencia legible (ej: para placas, pedidos, reservas)
    public static String generarCodigo(String prefijo, Long id) {
        return prefijo + String.format("%04d", id);  // ej: PLT-0001, RES-0007, PAR-0012
    }
}

Cuándo usar @Component en vez de clase estática

✅ Clase estática — para lógica pura

Cuando los métodos no dependen de ningún bean de Spring ni de configuración externa. Solo reciben parámetros y devuelven un resultado.

// Uso directo sin inyección — en el Service o Validator
TextoUtils.normalizarNombre(plato.getNombre());
FechaUtils.esFechaFutura(reserva.getFechaHora());
CalculoUtils.redondear(precio * cantidad);
⚙️ @Component — cuando necesita configuración

Cuando la utility necesita leer valores de application.yml con @Value. Raro — la mayoría de Utils son clases estáticas puras.

// Solo si necesitas leer application.yml
@Component
public class ConfigUtils {
  @Value("${restaurante.capacidad-max}")
  private int capacidadMaxima;

  public boolean superaCapacidad(int comensales) {
    return comensales > capacidadMaxima;
  }
}

Resumen — la cadena de responsabilidades:
Dominio → comportamiento propio del objeto (estaDisponible, activar, desactivar, puedeTransicionarA)
Validator → reglas de negocio que cruzan objetos (¿el nombre es único? ¿la mesa tiene cuenta?)
Utils → cálculos y transformaciones genéricas sin lógica de negocio (formatear, calcular, normalizar)
Service → orquesta: llama al Validator, usa Utils, opera sobre el dominio
Mapper → traduce entre capas — RequestDTO a dominio y dominio a ResponseDTO. Con MapStruct es solo declarativo, sin lógica.
Controller → recibe, delega al Service via Mapper, responde

// controller/PlatoController.java
@RestController
@RequestMapping("/api/v1/platos")
@RequiredArgsConstructor
@Slf4j
// Anotaciones Swagger (Paso 8)
@Tag(name = "Platos", description = "Gestión de la carta del restaurante")
public class PlatoController {

    // ✅ El Mapper se inyecta AQUÍ — no en el Service
    private final IPlatoService platoService;
    private final PlatoMapper   platoMapper;

    // ── GET /api/v1/platos ──────────────────────────────────────
    @GetMapping
    @Operation(summary = "Obtener todos los platos")
    public ResponseEntity<List<PlatoResponseDTO>> obtenerTodos() {
        log.info("GET /api/v1/platos");
        List<Plato> platos = platoService.obtenerTodos();
        // MapperOut: List<Plato> → List<PlatoResponseDTO>
        return ResponseEntity.ok(
            platos.stream().map(platoMapper::toResponse).toList()
        );
    }

    // ── GET /api/v1/platos/{id} ─────────────────────────────────
    @GetMapping("/{id}")
    @Operation(summary = "Obtener plato por ID")
    public ResponseEntity<PlatoResponseDTO> obtenerPorId(
            @PathVariable Long id) {
        Plato plato = platoService.obtenerPorId(id);
        return ResponseEntity.ok(platoMapper.toResponse(plato));
    }

    // ── POST /api/v1/platos ─────────────────────────────────────
    @PostMapping
    @Operation(summary = "Crear un nuevo plato")
    public ResponseEntity<PlatoResponseDTO> crear(
            @RequestBody @Valid PlatoRequestDTO dto) {
        log.info("POST /api/v1/platos - nombre={}", dto.getNombre());

        // MapperIn: RequestDTO → dominio
        Plato plato = platoMapper.toDomain(dto);

        // Service recibe dominio, devuelve dominio
        Plato creado = platoService.crear(plato);

        // MapperOut: dominio → ResponseDTO
        return ResponseEntity
            .status(HttpStatus.CREATED)  // ← 201, no 200
            .body(platoMapper.toResponse(creado));
    }

    // ── PATCH /api/v1/platos/{id}/disponible ────────────────────
    @PatchMapping("/{id}/disponible")
    @Operation(summary = "Cambiar disponibilidad de un plato")
    public ResponseEntity<PlatoResponseDTO> cambiarDisponibilidad(
            @PathVariable Long id,
            @RequestParam boolean disponible) {
        Plato actualizado = platoService.cambiarDisponibilidad(id, disponible);
        return ResponseEntity.ok(platoMapper.toResponse(actualizado));
    }

    // ── DELETE /api/v1/platos/{id} ──────────────────────────────
    @DeleteMapping("/{id}")
    @Operation(summary = "Eliminar un plato")
    public ResponseEntity<Void> eliminar(@PathVariable Long id) {
        platoService.eliminar(id);
        return ResponseEntity.noContent().build();  // ← 204, sin body
    }
}

El patrón del Controller tiene siempre la misma forma:
1. Recibe el request (con @Valid si tiene body)
2. Llama al MapperIn: platoMapper.toDomain(dto)
3. Delega al Service: recibe objeto de dominio, obtiene objeto de dominio
4. Llama al MapperOut: platoMapper.toResponse(resultado)
5. Responde con el código HTTP correcto: 200, 201, 204

// exception/GlobalExceptionHandler.java
@RestControllerAdvice  // intercepta todos los Controllers
@Slf4j
public class GlobalExceptionHandler {

    // 404 — Recurso no encontrado
    @ExceptionHandler(RecursoNoEncontradoException.class)
    public ResponseEntity<ErrorResponseDTO> handleNotFound(
            RecursoNoEncontradoException ex,
            HttpServletRequest request) {
        log.warn("RecursoNoEncontrado: {}", ex.getMessage());
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(buildError(404, "Not Found",
                        ex.getMessage(), request.getRequestURI()));
    }

    // 409 — Conflicto (nombre duplicado, mesa ocupada, etc.)
    @ExceptionHandler(ConflictoException.class)
    public ResponseEntity<ErrorResponseDTO> handleConflicto(
            ConflictoException ex, HttpServletRequest request) {
        return ResponseEntity.status(HttpStatus.CONFLICT)
                .body(buildError(409, "Conflict",
                        ex.getMessage(), request.getRequestURI()));
    }

    // 422 — Regla de negocio / estado inválido
    @ExceptionHandler({EstadoInvalidoException.class, ReglaDeNegocioException.class})
    public ResponseEntity<ErrorResponseDTO> handleNegocio(
            RuntimeException ex, HttpServletRequest request) {
        return ResponseEntity.status(HttpStatus.UNPROCESSABLE_ENTITY)
                .body(buildError(422, "Unprocessable Entity",
                        ex.getMessage(), request.getRequestURI()));
    }

    // 400 — Validación de input (@Valid falló)
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponseDTO> handleValidacion(
            MethodArgumentNotValidException ex,
            HttpServletRequest request) {
        String mensaje = ex.getBindingResult().getFieldErrors().stream()
                .map(e -> e.getField() + ": " + e.getDefaultMessage())
                .collect(Collectors.joining(", "));
        return ResponseEntity.status(HttpStatus.BAD_REQUEST)
                .body(buildError(400, "Bad Request",
                        mensaje, request.getRequestURI()));
    }

    // 500 — Genérico (siempre al final — el más general)
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponseDTO> handleGenerico(
            Exception ex, HttpServletRequest request) {
        log.error("Error inesperado: {}", ex.getMessage(), ex);
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                .body(buildError(500, "Internal Server Error",
                        "Error inesperado del servidor",
                        request.getRequestURI()));
    }

    private ErrorResponseDTO buildError(int status, String error,
                                            String message, String path) {
        return ErrorResponseDTO.builder()
                .timestamp(LocalDateTime.now())
                .status(status)
                .error(error)
                .message(message)
                .path(path)
                .build();
    }
}
🚨
¿Por qué el @ExceptionHandler de Exception.class va al final? Spring evalúa los handlers de más específico a más general. Si el genérico estuviera primero, capturaría todo antes de que los específicos puedan actuar. Siempre: excepciones específicas primero, Exception.class al final.
⏸ Pausa rápida Excepciones — prueba en vivo
Haz un POST con body vacío — ¿recibes 400 con el ErrorResponseDTO?
Si recibes un HTML o un stack trace crudo → el GlobalExceptionHandler no está configurado o hay un error de compilación. Si recibes 400 con JSON → funciona correctamente.
Haz un GET con un ID que no existe — ¿recibes 404 con mensaje claro?
Debe llegar: { "status": 404, "error": "Not Found", "message": "No existe Plato con id=99", "path": "/api/v1/platos/99" }
¿Qué pasa si no tienes @ExceptionHandler para una excepción específica?
Cae en el @ExceptionHandler(Exception.class) genérico → devuelve 500 con mensaje genérico. Por eso es importante tener un handler específico para cada excepción del dominio.

    @GetMapping("/{id}")
    @Operation(summary = "Ver detalle de un plato")
    @ApiResponses({
        @ApiResponse(responseCode = "200", description = "Plato encontrado"),
        @ApiResponse(responseCode = "404", description = "Plato no existe o no disponible")

    public ResponseEntity<PlatoResponseDTO> verDetalle(@PathVariable Long id) {
        Plato plato = platoService.obtenerPorId(id);
        if (!plato.estaDisponible()) {
            throw new RecursoNoEncontradoException("Plato disponible", id);
        }
        return ResponseEntity.ok(platoMapper.toResponse(plato));
    }

    // Filtrar por categoría — sin paginación por ahora
    @GetMapping("/categoria/{categoria}")
    @Operation(summary = "Ver carta filtrada por categoría")
    @ApiResponse(responseCode = "200", description = "Platos de la categoría")

            @PathVariable String categoria) {
        return ResponseEntity.ok(
            platoService.obtenerPorCategoria(categoria).stream()
                .filter(Plato::estaDisponible)
                .map(platoMapper::toResponse)
                .toList()
        );
    }

Pruebas del Service, Validator y Utils
💡
¿Qué se prueba y qué no? Se prueba la lógica — ServiceImpl, Validator, Utils. No se prueba el Controller con pruebas unitarias (eso es prueba de integración). El Controller no tiene lógica propia — su corrección se verifica en Swagger/Postman.

Pruebas del ServiceImpl — con Mockito

// PlatoServiceImplTest.java
@ExtendWith(MockitoExtension.class)
class PlatoServiceImplTest {

    @Mock
    private IPlatoValidator validator;  // doble controlado — no ejecuta lógica real

    @InjectMocks
    private PlatoServiceImpl service;  // la clase real con el mock inyectado

    // ── Caso exitoso ────────────────────────────────────────────
    @Test
    @DisplayName("crear - guarda el plato y le asigna un ID")
    void crear_platoCorrecto_guardaYRetorna() {
        Plato entrada = Plato.builder()
                .nombre("Bandeja Paisa").precio(28000.0)
                .categoria("PRINCIPALES").disponible(true).build();

        Plato resultado = service.crear(entrada);

        assertNotNull(resultado.getId());
        assertEquals("Bandeja Paisa", resultado.getNombre());
        // Verifica que el validator fue llamado exactamente 1 vez
        verify(validator, times(1)).validarNombreUnico(
                eq("Bandeja Paisa"), any());
    }

    // ── Recurso no encontrado ────────────────────────────────────
    @Test
    @DisplayName("obtenerPorId - ID inexistente lanza RecursoNoEncontradoException")
    void obtenerPorId_noExiste_lanzaExcepcion() {
        assertThrows(RecursoNoEncontradoException.class,
                () -> service.obtenerPorId(99L));
    }

    // ── El validator rechaza (nombre duplicado) ──────────────────
    @Test
    @DisplayName("crear - nombre duplicado lanza ConflictoException")
    void crear_nombreDuplicado_lanzaConflicto() {
        // Configura el mock para que lance la excepción al llamar validarNombreUnico
        doThrow(new ConflictoException("Nombre duplicado"))
                .when(validator).validarNombreUnico(any(), any());

        Plato plato = Plato.builder().nombre("Bandeja Paisa")
                .precio(28000.0).categoria("PRINCIPALES").build();

        assertThrows(ConflictoException.class,
                () -> service.crear(plato));
    }

    // ── Lista vacía devuelve lista vacía, no null ────────────────
    @Test
    @DisplayName("obtenerTodos - sin platos devuelve lista vacía")
    void obtenerTodos_sinPlatos_devuelveListaVacia() {
        List<Plato> resultado = service.obtenerTodos();
        assertNotNull(resultado);
        assertTrue(resultado.isEmpty());
    }

    // ── Solo devuelve los disponibles ────────────────────────────
    @Test
    @DisplayName("obtenerDisponibles - filtra correctamente")
    void obtenerDisponibles_filtraSoloDisponibles() {
        service.crear(Plato.builder().nombre("A").precio(10.0)
                .categoria("X").disponible(true).build());
        service.crear(Plato.builder().nombre("B").precio(10.0)
                .categoria("X").disponible(false).build());

        List<Plato> resultado = service.obtenerDisponibles();

        assertEquals(1, resultado.size());
        assertEquals("A", resultado.get(0).getNombre());
    }

    // ── cambiarDisponibilidad ────────────────────────────────────
    @Test
    @DisplayName("cambiarDisponibilidad - desactiva un plato existente")
    void cambiarDisponibilidad_desactiva_correctamente() {
        Plato creado = service.crear(Plato.builder().nombre("Sopa")
                .precio(15.0).categoria("ENTRADAS").disponible(true).build());

        Plato resultado = service.cambiarDisponibilidad(creado.getId(), false);

        assertFalse(resultado.estaDisponible());
    }
}

Pruebas del Validator — sin mocks, lógica real

// PlatoValidatorTest.java
// El Validator NO tiene dependencias — se prueba sin mocks
class PlatoValidatorTest {

    private final PlatoValidator validator = new PlatoValidator();

    @Test
    @DisplayName("validarNombreUnico - nombre nuevo no lanza excepción")
    void validarNombreUnico_nombreNuevo_noLanza() {
        List<Plato> existentes = List.of(
            Plato.builder().nombre("Ajiaco").build()
        );
        // No debe lanzar excepción
        assertDoesNotThrow(() ->
            validator.validarNombreUnico("Bandeja Paisa", existentes));
    }

    @Test
    @DisplayName("validarNombreUnico - nombre duplicado (case-insensitive) lanza ConflictoException")
    void validarNombreUnico_nombreDuplicado_lanzaConflicto() {
        List<Plato> existentes = List.of(
            Plato.builder().nombre("Ajiaco").build()
        );
        assertThrows(ConflictoException.class, () ->
            validator.validarNombreUnico("AJIACO", existentes));
    }

    @Test
    @DisplayName("validarDisponibleParaPedido - plato agotado lanza ReglaDeNegocioException")
    void validarDisponible_platoAgotado_lanza() {
        Plato agotado = Plato.builder().disponible(false).nombre("Ajiaco").build();
        assertThrows(ReglaDeNegocioException.class, () ->
            validator.validarDisponibleParaPedido(agotado));
    }
}

Los 5 escenarios que siempre debes cubrir en el Service

✅
Happy path — el flujo normal funciona y devuelve el objeto correcto
✅
Recurso no encontrado — lanza RecursoNoEncontradoException con el ID correcto
✅
Duplicado / conflicto — el validator rechaza y lanza ConflictoException
✅
Estado inválido — transición rechazada lanza EstadoInvalidoException
✅
Lista vacía — devuelve lista vacía, nunca null ni excepción
⏸ Pausa rápida Pruebas — comprueba que entiendes
¿Cuál es la diferencia entre @Mock y @InjectMocks?
@Mock crea un doble vacío de una dependencia — no ejecuta código real. @InjectMocks crea la clase real bajo prueba e inyecta los @Mock en su constructor. El SUT (Subject Under Test) siempre es @InjectMocks.
¿Por qué el Validator se prueba sin mocks?
Porque el Validator no tiene dependencias inyectadas — solo recibe parámetros. Lo que quieres probar es su lógica real: que sí rechaza un nombre duplicado y que no rechaza uno nuevo. Con un mock estarías probando el mock, no el Validator.
¿Qué hace verify(validator, times(1)).metodo()?
Verifica que el mock fue llamado exactamente 1 vez con ese método. Es útil para confirmar que el Service sí delegó la validación al Validator, sin que el test dependa del resultado de esa validación.

¿Tu Controller está completo? — Revisa antes de pasar al siguiente dominio

Por cada dominio del restaurante

☐
Dominio — model/domain/. @Data @Builder @AllArgsConstructor. Métodos de comportamiento propios (no validaciones de formato). Enum con lógica de transición si tiene estados.
☐
RequestDTO — model/dto/request/. Solo Bean Validation (@NotBlank, @Positive…). Sin lógica.
☐
ResponseDTO — model/dto/response/. Solo los campos que el cliente necesita. Sin lógica.
☐
Mapper — mapper/. Interfaz con @Mapper(componentModel="spring"). toDomain() + toResponse() + toResponseList(). Inyectado en el Controller.
☐
Interfaz Service — service/. Métodos reciben y devuelven dominio. Nunca DTOs.
☐
ServiceImpl — service/impl/. @Service @Slf4j @RequiredArgsConstructor. ConcurrentHashMap + AtomicLong. Streams en todos los métodos. Logs en operaciones clave.
☐
Interfaz Validator — validator/. Contrato de validaciones de negocio. Inyectada en ServiceImpl via interfaz.
☐
ValidatorImpl — @Component. Cada método valida una regla, lanza excepción tipada. Sin anotaciones de Spring MVC.
☐
Utils (si aplica) — util/. Clase final estática con constructor privado. Solo si la lógica es compartida entre dominios.
☐
Controller — controller/. @RequestMapping("/api/v1/nombre"). Inyecta Service + Mapper. Patrón: toDomain → service → toResponse. @Valid en @RequestBody. Códigos HTTP correctos.
☐
Excepciones — Una clase por tipo de error. GlobalExceptionHandler las captura todas. Handlers específicos antes que Exception.class.
☐
Swagger — @Tag en la clase. @Operation + @ApiResponses en cada endpoint. Códigos de éxito y error documentados.
☐
Pruebas — ServiceImpl con @Mock validator + @InjectMocks service. Validator sin mocks. Utils con casos límite y nulls. Los 5 escenarios cubiertos.

Los 5 errores más comunes — revisa que no los tengas:
❌ El Mapper inyectado en el ServiceImpl — va en el Controller
❌ El Service recibiendo o devolviendo DTOs — solo dominio
❌ El Controller con lógica de negocio — solo recibe, traduce y delega
❌ Validaciones de formato en el Validator — eso es del DTO con @Valid
❌ POST respondiendo 200 en vez de 201, DELETE con body en vez de 204 sin body
⏸ Repaso de cierre Sin mirar la guía — ¿puedes responder estas?
¿Por qué MenuController y PlatoController inyectan el mismo IPlatoService?
Porque la lógica es la misma — ambos trabajan con objetos Plato. La diferencia es semántica: el Menú filtra solo disponibles y no tiene endpoints de escritura. Duplicar el Service para eso generaría deuda técnica y dos lugares donde corregir bugs.
Un PUT recibe un nombre que ya tiene el propio plato. ¿Debe lanzar 409?
No. Al validar nombre único en actualizar(), debes excluir el propio plato del stream con .filter(p -> !p.getId().equals(id)). Si no lo haces, el PUT del mismo nombre siempre falla aunque sea el nombre correcto del plato.
¿Qué código devuelve un DELETE exitoso y qué body tiene?
204 No Content, sin body: ResponseEntity.noContent().build(). Si devuelve 200 o body, está mal.
¿Cuándo se usa 409 y cuándo 422?
409 Conflict: hay un conflicto de estado — el recurso ya existe con ese nombre, o la mesa ya tiene cuenta abierta. 422 Unprocessable Entity: el formato del request es válido pero la regla de negocio lo rechaza — intentar pasar un pedido de LISTO a RECIBIDO, o eliminar un plato con pedidos activos.

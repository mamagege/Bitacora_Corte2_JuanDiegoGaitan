SECCIÓN 01
Estándares de un API REST

Un API sin estándares es como un restaurante donde cada mesero hace las cosas a su manera — el cliente nunca sabe qué esperar. Los estándares garantizan coherencia sin importar quién desarrolla ni dónde.

URLs claras y consistentes

Sustantivos en plural, jerarquías lógicas. /platos no /getPlatos. /platos/5/ingredientes no /getIngredientesDePlato5.

Verbos HTTP correctos

GET para leer, POST para crear, PUT para reemplazar, PATCH para actualizar parcialmente, DELETE para eliminar. No uses GET para crear.

Respuesta consistente

Siempre el mismo formato de respuesta — éxito y error. El cliente no debería adivinar si viene un array o un objeto dependiendo del endpoint.

Códigos HTTP correctos

Cada verbo tiene sus códigos esperados. No todos los éxitos son 200 — POST exitoso es 201, DELETE exitoso es 204. Verlo abajo en detalle.

Mensajes de error descriptivos

Un 500 sin mensaje es como un mesero que se desmaya. El error debe decirle al cliente qué hizo mal, con un mensaje humano y un código interno.

Documentación siempre actualizada

Swagger/OpenAPI genera la documentación automáticamente desde el código. Si el código cambia, la doc cambia — sin esfuerzo manual.

Códigos HTTP por verbo — la referencia completa

Cada verbo tiene sus propios códigos de éxito y sus propios errores esperados. Aprenderlos te evita devolver un 200 cuando creaste algo, o un 500 cuando simplemente no encontraste el recurso.

Los 3 códigos que más se confunden:
200 vs 201 — 200 es "todo bien, aquí están los datos". 201 es "creé algo nuevo". POST siempre debe devolver 201, nunca 200.
404 vs 422 — 404 es "ese recurso no existe". 422 es "el recurso existe pero la operación viola una regla del dominio".
400 vs 422 — 400 es "el formato del request está mal" (@Valid falló). 422 es "el formato está bien, pero el negocio lo rechaza".

SECCIÓN 01-B
Versionamiento de API

Imagina que el frontend ya está en producción usando /api/v1/platos. Ahora necesitas cambiar la estructura de la respuesta — agregar un campo, renombrar otro, eliminar uno que usaba el cliente. Si cambias el endpoint directamente, el frontend se rompe. La solución: versionar el API.

¿Cuándo versionar?

Cuando un cambio rompe la compatibilidad con los clientes existentes: eliminar un campo de la respuesta, cambiar el tipo de un campo, renombrar un campo obligatorio, cambiar la semántica de un endpoint. Agregar campos opcionales normalmente no requiere nueva versión.

¿Cuándo NO versionar?

Cuando el cambio es aditivo y no rompe nada: agregar un campo opcional nuevo a la respuesta, agregar un endpoint nuevo, mejorar el rendimiento sin cambiar el contrato. Los clientes que no usan el campo nuevo simplemente lo ignoran.

Las tres estrategias — y cuál usar

✅ URL VERSIONING
/api/v1/platos
/api/v2/platos

La más común y visible. La versión vive en la URL. Fácil de probar, fácil de enrutar, fácil de documentar en Swagger. La que vas a usar tú.

⚠️ HEADER VERSIONING
Accept: application/
vnd.app.v2+json

Más "pura" en REST — la URL no cambia. Pero es más difícil de probar, no aparece bien en Swagger y confunde a equipos pequeños.

⚠️ QUERY PARAM
/platos?version=2

Fácil de implementar pero ensucia las URLs, complica el cacheo y mezcla versionamiento con filtros de negocio. No recomendado.

⏸ Pausa rápida Versionamiento — ¿cuándo lo necesitas?
¿Agregar un campo nuevo a la respuesta requiere una nueva versión de la API?

Logging — El registro de vida de tu restaurante

Un restaurante sin registros no sabe qué salió mal, quién pidió qué, ni en qué momento colapsó la cocina. El logging es lo mismo en software: el registro estructurado de todo lo que le pasa a la aplicación.

// En cualquier clase del proyecto — con Lombok es un @Slf4j
@Service
@Slf4j                          // ← Lombok genera: private static final Logger log = LoggerFactory.getLogger(...)
@RequiredArgsConstructor
public class PlatoServiceImpl implements IPlatoService {

    private final Map<Long, Plato> platos = new HashMap<>();
    private final PlatoMapperIn    mapperIn;
    private final PlatoMapperOut   mapperOut;

    @Override
    public PlatoResponseDTO crear(PlatoRequestDTO dto) {
        log.info("Creando plato con nombre '{}'", dto.nombre());           // INFO — evento normal

        boolean nombreDuplicado = platos.values().stream()
            .anyMatch(p -> p.getNombre().equalsIgnoreCase(dto.nombre()));

        if (nombreDuplicado) {
            log.warn("Intento de crear plato duplicado: '{}'", dto.nombre()); // WARN — no es error pero es sospechoso
            throw new PlatoYaExisteException("Ya existe un plato con ese nombre: " + dto.nombre());
        }

        Plato plato = mapperIn.toDomain(dto);
        plato.setId(generarId());
        platos.put(plato.getId(), plato);

        log.info("Plato '{}' creado con id={}", plato.getNombre(), plato.getId()); // INFO — éxito
        return mapperOut.toDTO(plato);
    }

    @Override
    public PlatoResponseDTO buscarPorId(Long id) {
        log.debug("Buscando plato con id={}", id);                         // DEBUG — detalle de búsqueda
        Plato plato = platos.get(id);
        if (plato == null) {
            log.error("Plato con id={} no encontrado", id);               // ERROR — fallo que hay que manejar
            throw new PlatoNoEncontradoException("Plato no encontrado con id: " + id);
        }
        return mapperOut.toDTO(plato);
    }
}

SECCIÓN 04
Validaciones — Input vs Negocio
⚖️
La regla de oro: Las validaciones de input van en el DTO (con anotaciones Bean Validation). Las validaciones de negocio van en el Service (con excepciones propias). Nunca al revés, nunca mezcladas.

📥 Validación de INPUT — en el DTO

  • → ¿El formato es correcto?
  • → ¿El campo está presente?
  • → ¿El número está en rango?
  • → @NotNull, @NotBlank, @Min, @Max
  • → Spring la dispara automáticamente con @Valid
  • → Da 400 Bad Request

⚙️ Validación de NEGOCIO — en el Service

  • ¿Cumple la regla del dominio?
  • ¿El plato ya existe con ese nombre?
  • ¿El pedido está en estado modificable?
  • Excepciones propias tipadas
  • Tú la dispararas manualmente con throw
  • Da 409 Conflict o 422 Unprocessable

Bean Validation en el DTO del restaurante

// dto/PlatoRequestDTO.java — validaciones de INPUT con Bean Validation
public record PlatoRequestDTO(

    @NotBlank(message = "El nombre del plato es obligatorio")
    @Size(min = 2, max = 80, message = "El nombre debe tener entre 2 y 80 caracteres")
    String nombre,

    @NotNull(message = "El precio es obligatorio")
    @DecimalMin(value = "0.01", message = "El precio debe ser mayor a cero")

// exception/GlobalExceptionHandler.java
@RestControllerAdvice          // ← intercepta excepciones de TODOS los controllers
@Slf4j
public class GlobalExceptionHandler {

    // ── Excepciones de input (Bean Validation) → 400 ─────────────────────
    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public ErrorResponseDTO handleValidacion(
            MethodArgumentNotValidException ex,
            HttpServletRequest request) {

        // Extrae TODOS los errores de validación en una sola lista
        String errores = ex.getBindingResult().getFieldErrors().stream()
            .map(e -> e.getField() + ": " + e.getDefaultMessage())
            .collect(Collectors.joining(" | "));

        log.warn("Validación de input fallida: {}", errores);

        return ErrorResponseDTO.of(400, "Datos de entrada inválidos", errores, request.getRequestURI());
    }

    // ── Recurso no encontrado → 404 ───────────────────────────────────────
    @ExceptionHandler(PlatoNoEncontradoException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public ErrorResponseDTO handleNoEncontrado(
            PlatoNoEncontradoException ex, HttpServletRequest request) {

        log.warn("Recurso no encontrado: {}", ex.getMessage());
        return ErrorResponseDTO.of(404, "No encontrado", ex.getMessage(), request.getRequestURI());
    }

    // ── Conflicto de negocio → 409 ────────────────────────────────────────
    @ExceptionHandler(PlatoYaExisteException.class)
    @ResponseStatus(HttpStatus.CONFLICT)
    public ErrorResponseDTO handleConflicto(
            PlatoYaExisteException ex, HttpServletRequest request) {

        log.warn("Conflicto de negocio: {}", ex.getMessage());
        return ErrorResponseDTO.of(409, "Conflicto", ex.getMessage(), request.getRequestURI());
    }

    // ── Estado inválido de negocio → 422 ─────────────────────────────────
    @ExceptionHandler(EstadoInvalidoException.class)
    @ResponseStatus(HttpStatus.UNPROCESSABLE_ENTITY)
    public ErrorResponseDTO handleEstadoInvalido(
            EstadoInvalidoException ex, HttpServletRequest request) {

        log.warn("Estado de negocio inválido: {}", ex.getMessage());
        return ErrorResponseDTO.of(422, "Estado inválido", ex.getMessage(), request.getRequestURI());
    }

    // ── Cualquier otro error no controlado → 500 ─────────────────────────
    @ExceptionHandler(Exception.class)
    @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
    public ErrorResponseDTO handleGeneral(Exception ex, HttpServletRequest request) {
        log.error("Error no controlado: {}", ex.getMessage(), ex);   // ← full stack trace en ERROR
        return ErrorResponseDTO.of(500, "Error interno", "Algo salió mal, intenta de nuevo", request.getRequestURI());
        // NUNCA expongas ex.getMessage() aquí — puede filtrar info sensible
    }
}

// ── En PedidoService: resumen del día con streams ─────────────────────
public ResumenDiaDTO resumenDelDia() {

    long totalPedidos = pedidos.stream().count();

    double ingresoTotal = pedidos.stream()
        .flatMap(p -> p.getItems().stream())        // aplana la lista de items de todos los pedidos
        .mapToDouble(item -> item.getPrecio() * item.getCantidad())
        .sum();

    Map<String, Long> platosMasPedidos = pedidos.stream()
        .flatMap(p -> p.getItems().stream())
        .collect(Collectors.groupingBy(
            item -> item.getNombrePlato(),
            Collectors.counting()
        ));

    return new ResumenDiaDTO(totalPedidos, ingresoTotal, platosMasPedidos);
}
⏸ Pausa rápida Streams — prueba en tu código
¿Cuál es la diferencia entre map() y flatMap()?
map() transforma cada elemento 1-a-1. flatMap() aplana listas dentro de listas — si cada pedido tiene una lista de items, flatMap convierte esa lista de listas en una sola secuencia de items.
¿Por qué usar anyMatch() en vez de filter().count() > 0?
anyMatch() para en cuanto encuentra el primer elemento que cumple la condición. filter().count() procesa toda la colección aunque ya encontró una coincidencia — es innecesariamente lento.
¿Qué hace groupingBy()?
Agrupa los elementos por una clave y los colecta en un Map — el equivalente de un GROUP BY en SQL. Muy útil para los reportes del restaurante.

Vocabulario de dobles de prueba

Stub

Devuelve datos predefinidos. No verifica si fue llamado. Solo "responde" lo que le programas. Útil para simular el Repository con datos fijos.

Mock

Devuelve datos predefinidos Y verifica si fue llamado (cuántas veces, con qué argumentos). Con Mockito: verify(mock, times(1)).metodo().

Spy

Envuelve un objeto real — llama el método real pero también verifica las interacciones. Útil cuando quieres comportamiento real pero monitoreado.

Flecha sólida = síncrono (espera respuesta). Flecha discontinua = respuesta de retorno. Flecha abierta = asíncrono (no espera).

Activation bar

Rectángulo delgado sobre la lifeline — indica que ese componente está activo procesando una petición.

Fragmentos (alt, opt, loop)

alt para condiciones (como if/else). opt para acciones opcionales. loop para repeticiones. Se etiquetan en la esquina superior izquierda de la caja.

🔌 Paso 3 — Identifica qué servicios se reutilizan

Antes de implementar, hazte estas preguntas por cada funcionalidad:

¿Necesito datos de otro dominio?

Si PedidoService necesita saber si un plato existe → inyecta IPlatoService. Si ReservaService necesita saber si una mesa tiene pedido activo → inyecta IPedidoService. Siempre via interfaz.

¿Existe ya un método que hace esto?

Si MenuController y PlatoController ambos listan platos → el mismo método IPlatoService.obtenerDisponibles() sirve a los dos. No duplicar lógica — ampliar la interfaz.

// Ejemplo: PedidoServiceImpl reutiliza IPlatoService
@Service
@Slf4j
@RequiredArgsConstructor
public class PedidoServiceImpl implements IPedidoService {

    private final IPlatoService      platoService;   // ← reutiliza otro Service via interfaz
    private final PedidoMapperIn     mapperIn;
    private final PedidoMapperOut    mapperOut;

    private final List<Pedido> pedidos = new ArrayList<>(); // en memoria por ahora

    @Override
    public PedidoResponseDTO confirmar(PedidoRequestDTO dto) {
        log.info("Confirmando pedido para mesa {}", dto.mesa());

        // Valida cada plato reutilizando IPlatoService — no repite esa lógica aquí
        List<Plato> platosDelPedido = dto.idPlatos().stream()
            .map(id -> {
                PlatoResponseDTO plato = platoService.buscarPorId(id); // ← reutiliza!
                if (!plato.disponible()) {
                    throw new PlatoNoDisponibleException("Plato agotado: " + plato.nombre());
                }
                return mapperIn.toPlatoDomain(plato);
            })
            .toList();

        Pedido pedido = mapperIn.toDomain(dto, platosDelPedido);
        pedido.setId(generarId());
        pedido.setEstado(EstadoPedido.RECIBIDO);
        pedido.setFechaCreacion(LocalDateTime.now());
        pedidos.add(pedido);

        log.info("Pedido #{} creado para mesa {}", pedido.getId(), dto.mesa());
        return mapperOut.toDTO(pedido);
    }
}

// Ejemplo: ReporteServiceImpl reutiliza dos servicios
@Service
@RequiredArgsConstructor
public class ReporteServiceImpl implements IReporteService {

    private final IPedidoService pedidoService; // ← reutiliza pedidos
    private final IPlatoService  platoService;  // ← reutiliza platos

    @Override
    public ResumenDiaDTO resumenDelDia() {
        List<PedidoResponseDTO> pedidos = pedidoService.listarTodos();
        List<PlatoResponseDTO>  platos  = platoService.obtenerTodos();

        long totalPedidos = pedidos.stream().count();

        String platoMasPedido = pedidos.stream()
            .flatMap(p -> p.items().stream())
            .collect(Collectors.groupingBy(ItemDTO::nombrePlato, Collectors.counting()))
            .entrySet().stream()
            .max(Map.Entry.comparingByValue())
            .map(Map.Entry::getKey)
            .orElse("Sin pedidos");

        long platosDisponibles = platos.stream().filter(PlatoResponseDTO::disponible).count();

        return new ResumenDiaDTO(totalPedidos, platoMasPedido, platosDisponibles);
    }
}

⚙️ Paso 4 — Implementa funcionalidad por funcionalidad

El orden recomendado para cada funcionalidad es siempre el mismo — de adentro hacia afuera:

  • Entidad de negocio en domain/
    La clase pura: atributos, constructor, métodos de negocio. Sin anotaciones Spring ni JPA. Esta es la que va en el diagrama de clases.
  • DTOs en dto/request/ y dto/response/ con @Valid
    Record para el request con anotaciones Bean Validation. Record para el response sin lógica. Son los objetos de transferencia — nunca llegan al diagrama de clases.
  • Interfaz del Service en service/
    Define el contrato: qué métodos expone el Service, con qué tipos. Los controllers solo conocen esta interfaz.
  • Mappers en mapper/in/ y mapper/out/
    MapperIn: RequestDTO → Entidad de Negocio. MapperOut: Entidad de Negocio → ResponseDTO. Con @Mapping si los campos tienen nombre distinto.
  • Implementación del Service con @Slf4j, streams y excepciones
    Lógica de negocio, validaciones, logs en cada punto. Usa las colecciones en memoria (Map o List) para persistir por ahora.
  • Controller con @Valid, @Operation y respuestas HTTP correctas
    Solo recibe, delega al service y devuelve. No tiene lógica. Documenta con Swagger todos los posibles status codes.
  • Excepciones propias + GlobalExceptionHandler
    Crea la excepción de negocio, agrégala al handler. Todos los errores deben devolver el mismo ErrorResponseDTO.
  • Pruebas del Service con JUnit + Mockito
    Happy path, recurso no encontrado, duplicado, estado inválido, lista vacía. Ejecuta jacoco:report y verifica cobertura > 70%.

⏸ Repaso final Todo lo de hoy — cinco preguntas de cierre
¿Por qué MenuController y PlatoController pueden compartir IPlatoService?
Porque la lógica de buscar platos disponibles es la misma sin importar quién la pide. Duplicar esa lógica genera deuda técnica y dos lugares donde corregir bugs.
¿Qué diferencia hay entre el diagrama de clases y el de componentes?
El de clases muestra las entidades del dominio puro con atributos y métodos. El de componentes muestra la arquitectura — Controller, Service, Mapper, Repository — y sus interfaces de conexión.
¿Por qué no ponemos los DTOs en el diagrama de clases?
Los DTOs no tienen comportamiento de dominio ni representan conceptos del negocio. El diagrama de clases es del dominio puro, no de la infraestructura de transporte.
¿Cuándo justificas crear un Controller nuevo vs agregar un endpoint al existente?
Cuando la agrupación funcional es distinta — un Controller por dominio. Si los endpoints sirven a actores distintos sobre el mismo recurso, pueden ir en Controllers separados que comparten el mismo Service.
¿Puede un Service depender de otro Service?
Sí, siempre via interfaz. PedidoServiceImpl puede inyectar IPlatoService para verificar disponibilidad. Cuidado con dependencias circulares: si A depende de B y B de A, Spring no puede resolver la inyección.

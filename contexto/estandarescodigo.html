SECCIÓN 01
Tipos de Cobertura de Pruebas

La cobertura mide qué porcentaje de tu código fue ejecutado por las pruebas. No garantiza que el código sea correcto, pero sí que fue probado. Cada tipo de cobertura mide cosas distintas.

TipoQué mideEjemplo clave
Line Coverage% de líneas ejecutadas al menos una vez¿Corrió esta línea alguna vez?
Branch CoverageCada rama de if/else fue probada¿El if fue true Y false?
Function CoverageCada función fue llamada al menos una vez¿Se invocó calcularDescuento()?
Condition CoverageCada condición booleana evaluó true y falseEn a && b: ¿a fue false? ¿b fue false?
Path CoverageTodos los caminos posibles del programaEl más completo y difícil de alcanzar
Loop CoverageLos ciclos se ejecutaron 0, 1 y N veces¿El for corrió sin iteraciones?
💡
¿Por qué importa el tipo? Line Coverage al 100% no garantiza haber probado todas las ramas. Un if sin else tiene cobertura de línea completa aunque nunca se evalúe la condición como false.

Branch Coverage aquí requiere: Un test donde precio ≤ 0 (rama izquierda B), uno donde el cliente es VIP, uno donde no es VIP pero precio > 100, y uno donde no es VIP y precio ≤ 100. Son 4 ramas = 4 tests mínimos para Branch Coverage completa.

🧠 Preguntas de Repaso — Cobertura

¿Qué diferencia hay entre Branch Coverage y Condition Coverage?
Branch ve si cada camino del if/else se ejecutó. Condition mira cada sub-condición booleana dentro de la decisión por separado.
¿Es posible tener 100% Line Coverage y 0% Branch Coverage?
Sí — si solo hay código en el bloque if y nunca se prueba el else, todas las líneas se ejecutan pero la rama else no.
¿Por qué Path Coverage es la más difícil de lograr?
Porque el número de caminos crece exponencialmente con cada decisión. Con n decisiones hay 2ⁿ caminos posibles.

SECCIÓN 02
Sistemas con Estado vs Sin Estado

💾 CON ESTADO (Stateful)

  • El servidor recuerda al cliente entre peticiones
  • Guarda contexto de sesión
  • Útil para flujos largos y complejos
  • Más costoso en recursos del servidor
  • Difícil de escalar horizontalmente

🌐 SIN ESTADO (Stateless)

  • Cada petición es independiente
  • El cliente envía todo lo necesario
  • Más fácil de escalar
  • Más simple de implementar
  • REST es stateless por definición
Diagrama — Diferencia entre Stateful y Stateless

C->>SL: GET /perfil (Bearer: eyJhbG...) SL-->>C: ✅ Datos del token (sin memoria del servidor)
🎮
Tip de clase: Un MMORPG (World of Warcraft) es Stateful — el servidor sabe dónde estás en el mundo. Un restaurante de comida rápida es Stateless — cada vez que pides, eres un cliente nuevo.

SECCIÓN 03
Arquitectura Cliente–Servidor & MVC en Capas
📋
Las 3 reglas del patrón Cliente–Servidor: 1) El cliente pide, el servidor responde — nunca al revés.   2) El servidor no recuerda al cliente (stateless).   3) Muchos clientes hablan con el mismo servidor.

Las 4 Capas — Responsabilidades claras

CONTROLLER
El Mesero
Responsabilidad:
  • Recibe la petición HTTP
  • Extrae datos del request
  • Llama al Service
  • Devuelve el Response DTO
  • NO tiene lógica propia
SERVICE
La Cocina
Responsabilidad:
  • Contiene la lógica de negocio
  • Valida reglas del dominio
  • Llama al Repository
  • Transforma datos (Entidad ↔ DTO)
  • NO conoce HTTP
REPOSITORY
La Despensa
Responsabilidad:
  • Accede a la base de datos
  • Guarda y recupera datos
  • Solo habla SQL/JPA
  • NO conoce la API
  • NO tiene lógica de negocio
CLIENT
El Proveedor
Responsabilidad:
  • Accede a servicios externos
  • Abstrae APIs de terceros
  • Lógica de abstracciones externas
⚠️
Error común: Poner lógica de negocio en el Controller o consultas a la BD directamente desde el Controller. Cada capa debe respetar sus responsabilidades — esto es lo que hace que el código sea mantenible y testeable.

SECCIÓN 04
DTOs, Records, Enums, Entidades, MapperIn/Out & MapStruct
Diagrama — MapperIn y MapperOut: dónde vive cada uno

🔄
La regla de los dos Mappers:
MapperIn convierte lo que entra al Service — ya sea un RequestDTO del Controller o un Modelo que llega del Repository.
MapperOut convierte lo que sale del Service — hacia un ResponseDTO para el Controller, o hacia un Modelo para persistir en BD.
El Service solo opera con Entidades de Negocio — nunca toca DTOs ni Modelos directamente.

DTO (Data Transfer Object)

Objeto simple para transportar datos entre capas. No tiene lógica de negocio. Evita exponer directamente las entidades de la BD. Controla qué info entra y sale de la API.

Record (Java)

Forma concisa de crear DTOs inmutables. Auto-genera constructor, getters, equals, hashCode y toString. Ideal para DTOs y respuestas JSON en APIs.

Enum (Enumeración)

Tipo especial para representar un conjunto fijo de constantes. Muy usados para estados (ACTIVO, INACTIVO), roles, o categorías en APIs.

Mapper

Se encarga de transformar datos entre capas. Puede hacerse manual o con MapStruct (genera el código en tiempo de compilación automáticamente).

MapperIn — del DTO a la Entidad de Negocio (manual vs MapStruct)

// ──── MANUAL: MapperIn (Controller → Service) ────
// El Controller recibe un RequestDTO y el Service necesita una EntidadNegocio

// 1. El DTO que llega del cliente
public record PedidoRequestDTO(String producto, int cantidad, Long clienteId) {}

// 2. La Entidad de Negocio (sin anotaciones de BD)
public class Pedido {
    private String producto;
    private int cantidad;
    private Long clienteId;
    // + reglas de negocio, constructores, etc.
}

// 3. MapperIn — convierte RequestDTO → Pedido (Entidad de Negocio)
@Component
public class PedidoMapperIn {
    public Pedido toDomain(PedidoRequestDTO dto) {
        Pedido pedido = new Pedido();
        pedido.setProducto(dto.producto());
        pedido.setCantidad(dto.cantidad());
        pedido.setClienteId(dto.clienteId());
        return pedido;
    }
}

// ──── CON MAPSTRUCT: mismo resultado, cero código manual ────
@Mapper(componentModel = "spring")   // ← Spring inyecta el mapper automáticamente
public interface PedidoMapperIn {
    Pedido toDomain(PedidoRequestDTO dto);   // MapStruct genera la implementación
}

MapperOut — de la Entidad de Negocio al DTO de respuesta (y al Modelo)

// ──── MapperOut hacia el Controller (Entidad de Negocio → ResponseDTO) ────
public record PedidoResponseDTO(Long id, String producto, String estado) {}

// Manual
@Component
public class PedidoMapperOut {
    public PedidoResponseDTO toDTO(Pedido pedido) {
        return new PedidoResponseDTO(
            pedido.getId(),
            pedido.getProducto(),
            pedido.getEstado().name()
        );
    }
}

// Con MapStruct
@Mapper(componentModel = "spring")
public interface PedidoMapperOut {
    PedidoResponseDTO toDTO(Pedido pedido);
    PedidoEntity toEntity(Pedido pedido);  // ← también mapea al Modelo de BD
}

// ──── En el Service: así se usan los mappers ────
@Service
@RequiredArgsConstructor          // ← Lombok genera el constructor automáticamente
public class PedidoServiceImpl implements PedidoService {

    private final PedidoMapperIn  mapperIn;   // inyectado por Spring via constructor
    private final PedidoMapperOut mapperOut;
    private final PedidoRepository repository;

    @Override
    public PedidoResponseDTO crear(PedidoRequestDTO dto) {
        Pedido pedido   = mapperIn.toDomain(dto);         // 1. DTO → Entidad de negocio
        // ... lógica de negocio aquí ...
        PedidoEntity ent = mapperOut.toEntity(pedido);    // 2. Negocio → Modelo BD
        repository.save(ent);
        return mapperOut.toDTO(pedido);                   // 3. Negocio → ResponseDTO
    }
}

¿Qué pasa si los campos se llaman distinto? — @Mapping

MapStruct mapea automáticamente campos con el mismo nombre. Pero cuando el DTO y la Entidad tienen campos con nombres distintos, le dices cómo conectarlos con @Mapping.

Diagrama — campos distintos en DTO vs Entidad de Negocio
flowchart LR subgraph DTO["📥 PedidoRequestDTO"] direction TB F1["nombreProducto"] F2["cantidadUnidades"] F3["idCliente"] F4["precioUnitario"] end subgraph ENT["🎯 Pedido (Entidad Negocio)"] direction TB E1["producto"] E2["cantidad"] E3["clienteId"] E4["precio"] end F1 -- "@Mapping\nsource='nombreProducto'\ntarget='producto'" --> E1 F2 -- "@Mapping\nsource='cantidadUnidades'\ntarget='cantidad'" --> E2 F3 -- "@Mapping\nsource='idCliente'\ntarget='clienteId'" --> E3 F4 -- "@Mapping\nsource='precioUnitario'\ntarget='precio'" --> E4 style DTO fill:#eaf5fb style ENT fill:#e8f7ef 
// ──── Escenario: los campos tienen nombres distintos ────

// DTO que llega del cliente
public record PedidoRequestDTO(
    String nombreProducto,    // ← se llama "nombreProducto"
    int    cantidadUnidades,  // ← se llama "cantidadUnidades"
    Long   idCliente,         // ← se llama "idCliente"
    double precioUnitario     // ← se llama "precioUnitario"
) {}

// Entidad de Negocio (nombres internos distintos)
public class Pedido {
    private String producto;  // ← se llama "producto"
    private int    cantidad;  // ← se llama "cantidad"
    private Long   clienteId; // ← se llama "clienteId"
    private double precio;    // ← se llama "precio"
}

// ──── MapStruct con @Mapping para campos con nombre distinto ────
@Mapper(componentModel = "spring")
public interface PedidoMapperIn {

    @Mapping(source = "nombreProducto",  target = "producto")
    @Mapping(source = "cantidadUnidades", target = "cantidad")
    @Mapping(source = "idCliente",        target = "clienteId")
    @Mapping(source = "precioUnitario",   target = "precio")
    Pedido toDomain(PedidoRequestDTO dto);
    // MapStruct genera la implementación aplicando cada @Mapping declarado
}

// ──── También sirve para campos anidados (objetos dentro de objetos) ────
public record RestauranteRequestDTO(
    String nombre,
    String calleDir,       // campo plano
    String ciudadDir       // campo plano
) {}

public class Restaurante {
    private String    nombre;
    private Direccion direccion; // ← objeto anidado
}

public class Direccion {
    private String calle;
    private String ciudad;
}

@Mapper(componentModel = "spring")
public interface RestauranteMapperIn {

    @Mapping(source = "calleDir",  target = "direccion.calle")   // ← notación de punto
    @Mapping(source = "ciudadDir", target = "direccion.ciudad")  // ← para campos anidados
    Restaurante toDomain(RestauranteRequestDTO dto);
}

// ──── ¿Y si un campo del target NO debe mapearse? ────
@Mapper(componentModel = "spring")
public interface PedidoMapperOut {

    @Mapping(target = "fechaCreacion", ignore = true) // ← MapStruct lo ignora, tú lo seteas en el Service
    @Mapping(source = "estado",        target = "estadoDescripcion") // renombrar
    PedidoResponseDTO toDTO(Pedido pedido);
}
⚠️
Si un campo no tiene @Mapping y los nombres son distintos, MapStruct lo dejará como null en la clase generada — no lanzará error. Por eso es importante revisar los campos o activar unmappedTargetPolicy = ReportingPolicy.ERROR en el @Mapper para que falle en compilación si queda algo sin mapear. 
// Configuración estricta: falla en compilación si algún campo queda sin mapear
@Mapper(componentModel = "spring", unmappedTargetPolicy = ReportingPolicy.ERROR)
public interface PedidoMapperIn {

    @Mapping(source = "nombreProducto", target = "producto")
    // Si olvidas mapear "cantidadUnidades" → error de compilación, no en runtime ✅
    Pedido toDomain(PedidoRequestDTO dto);
}
✨
¿Por qué MapStruct y no ModelMapper? MapStruct genera el código de mapeo en tiempo de compilación — no usa Reflection en runtime, así que es más rápido, más seguro (errores se ven al compilar) y más fácil de depurar. ModelMapper sí usa Reflection en runtime, lo que lo hace más lento y los errores aparecen en ejecución.
🔑
Diferencia clave: Entidad de Negocio vs @Entity
La Entidad de Negocio tiene reglas y comportamiento, no depende de la BD.
La @Entity refleja cómo se guarda en la BD — no tiene lógica de negocio.

SECCIÓN 06
Diseño de APIs REST
📌
Para recordar: No toda API es REST, pero todo servicio REST es una API. REST es un conjunto de principios arquitectónicos, no un protocolo. El protocolo concreto es HTTP.

Verbos HTTP — La guía completa

VerboCRUDQué haceSeguroIdempotente
GETRead Obtener recurso — solo lectura, nunca modifica ✅ Seguro ✅ Idempotente
POSTCreate Crear nuevo recurso, procesa el body ❌ Inseguro ❌ No idempotente
PUTUpdate/Replace Reemplaza el recurso completo en la URL ❌ Inseguro ✅ Idempotente
PATCHUpdate/Partial Modifica solo algunas propiedades del recurso ❌ Inseguro ⚠️ Depende impl.
DELETEDelete Elimina el recurso identificado por la URL ❌ Inseguro ✅ Idempotente
🔁
Idempotencia — Ejecutar la misma petición 1 o N veces produce el mismo efecto en el estado del sistema. Importante: esto NO ocurre por arte de magia — debes implementarlo en tu servicio. PUT al mismo recurso con los mismos datos siempre da el mismo resultado. POST crea N recursos si se llama N veces.

Buenas Prácticas de URL Design

✅ Usa sustantivos en plural

/users ✅    /getUsers ❌    /user ❌

✅ Usa jerarquías lógicas padre-hijo

/restaurants/5/menu/3 ✅    /getMenuOfRestaurant5 ❌

✅ Query params para filtros y paginación

/menu?categoria=vegetariano&page=2 ✅ — nunca para identificar recursos

✅ Consistencia en nombres

No mezcles snake_case con kebab-case. No mezcles singular y plural. Elige uno y mantenlo.

🧠 Preguntas de Repaso — APIs REST

¿Por qué GET es considerado "seguro"?
Porque nunca modifica el estado del recurso en el servidor — solo lee y devuelve datos.
¿Cuál es la diferencia entre PUT y PATCH?
PUT reemplaza el recurso completo. PATCH solo modifica los campos especificados en el body.
¿Por qué usar /restaurants/{id}/orders en vez de /getOrdersOfRestaurant?
REST usa sustantivos y jerarquías, no verbos. Los verbos HTTP ya expresan la acción.

SECCIÓN 07
Inyección de Dependencias, Interfaces, IoC & Spring + Lombok
🌿
Principio de Inversión de Dependencias (DIP):
Los módulos de alto nivel no deben depender de módulos de bajo nivel. Ambos deben depender de abstracciones (interfaces). Esto logra bajo acoplamiento y alta cohesión.
Diagrama — ¿Por qué se inyecta la interfaz, no la clase concreta?

¿Cómo se define y usa una interfaz en Spring?

// 1. Defines la INTERFAZ — el "contrato" que cualquier implementación debe cumplir
public interface IPedidoService {
    PedidoResponseDTO crear(PedidoRequestDTO dto);
    PedidoResponseDTO buscarPorId(Long id);
    List<PedidoResponseDTO> listarTodos();
}

// 2. Creas la IMPLEMENTACIÓN — la clase que hace el trabajo real
@Service                           // ← Spring la registra como Bean
@RequiredArgsConstructor           // ← Lombok genera el constructor con los campos final
public class PedidoServiceImpl implements IPedidoService {

    private final PedidoRepository     repository;   // ← inyectado por Spring
    private final PedidoMapperIn       mapperIn;     // ← inyectado por Spring
    private final PedidoMapperOut      mapperOut;    // ← inyectado por Spring
    private final INotificacionService notificacion; // ← también es interfaz

    @Override
    public PedidoResponseDTO crear(PedidoRequestDTO dto) {
        Pedido pedido = mapperIn.toDomain(dto);
        // reglas de negocio...
        repository.save(mapperOut.toEntity(pedido));
        notificacion.enviar("Pedido creado: " + pedido.getId());
        return mapperOut.toDTO(pedido);
    }
}

// 3. El CONTROLLER depende de la INTERFAZ, no de la implementación
@RestController
@RequestMapping("/api/v1/pedidos")
@RequiredArgsConstructor           // ← Lombok hace el constructor
public class PedidoController {

    private final IPedidoService pedidoService;  // ← interfaz, no PedidoServiceImpl

    @PostMapping
    public PedidoResponseDTO crear(@RequestBody @Valid PedidoRequestDTO dto) {
        return pedidoService.crear(dto);          // ← llama al servicio sin saber qué implementación es
    }
}
🤔
¿Por qué poner private final IPedidoService y no PedidoServiceImpl?
Porque el Controller no debería saber cómo se implementa el servicio — solo sabe qué puede hacer (el contrato de la interfaz). Si mañana cambias la implementación (de base SQL a NoSQL, o para tests), el Controller no cambia ni una línea.

Las 3 formas de inyectar dependencias en Spring

// ❌ FORMA 1: Inyección por campo (@Autowired directo) — NO recomendada
@Service
public class PedidoServiceImpl implements IPedidoService {
    @Autowired
    private PedidoRepository repository;  // Spring inyecta, pero no puedes hacer final
    // Problema: no testeable fácilmente, el campo no puede ser final
}

// ⚠️ FORMA 2: Inyección por setter — rara vez usada
@Service
public class PedidoServiceImpl implements IPedidoService {
    private PedidoRepository repository;

    @Autowired
    public void setRepository(PedidoRepository repository) {
        this.repository = repository;
    }
}

// ✅ FORMA 3: Inyección por CONSTRUCTOR — RECOMENDADA (con Lombok es trivial)
@Service
@RequiredArgsConstructor          // Lombok genera: public PedidoServiceImpl(PedidoRepository repo) {...}
public class PedidoServiceImpl implements IPedidoService {

    private final PedidoRepository repository;   // final = inmutable, seguro
    private final PedidoMapperIn   mapperIn;
    // Spring detecta el único constructor y lo usa para inyectar
}

// Sin Lombok, el constructor sería manual:
@Service
public class PedidoServiceImpl implements IPedidoService {
    private final PedidoRepository repository;

    public PedidoServiceImpl(PedidoRepository repository) {  // Spring inyecta aquí
        this.repository = repository;
    }
}
🏆
¿Por qué constructor injection + Lombok es la combinación ganadora?
@RequiredArgsConstructor genera automáticamente el constructor con todos los campos final. Spring detecta ese único constructor y lo usa para inyectar. Las dependencias son inmutables (final), explícitas, y en tests puedes pasar mocks directamente sin frameworks especiales.

Reflection (Introspección)

Técnica para analizar clases en tiempo de ejecución. Permite saber propiedades, métodos, clases que extiende, ejecutar operaciones — todo sin conocer la clase de antemano. Es la base de IoC en Spring.

Annotations (@)

Metadatos en el código. Spring los lee via Reflection para entender la app. @Service dice "esto es un bean de negocio". @Repository dice "esto accede a BD". Sin ellos, Spring no sabe qué hacer con tu clase.

🧠 Preguntas de Repaso — DI, Interfaces e IoC

¿Por qué en el Controller ponemos IPedidoService (interfaz) y no PedidoServiceImpl?
Para depender de la abstracción, no del detalle. El Controller solo sabe qué puede hacer el servicio, no cómo lo hace. Esto permite cambiar la implementación sin tocar el Controller.
¿Qué hace @RequiredArgsConstructor de Lombok?
Genera automáticamente un constructor con todos los campos marcados como final. Spring usa ese constructor para inyectar las dependencias.
¿Cuál es la diferencia entre IoC e Inyección de Dependencias?
IoC es el principio general — el Framework controla el ciclo de vida de los objetos. La Inyección de Dependencias es el mecanismo concreto — Spring pasa las dependencias al constructor en lugar de que tú uses new.
¿Qué pasaría si tienes dos clases que implementan IPedidoService?
Spring lanzaría un error de ambigüedad. Se resuelve con @Primary en la implementación preferida, o con @Qualifier("nombreBean") en el punto de inyección.

// Ejemplo completo de un Controller básico en Spring Boot
@RestController
@RequestMapping("/api/v1/menu")
public class MenuController {

    private final MenuService menuService; // ← inyección por constructor (recomendada)

    public MenuController(MenuService menuService) {
        this.menuService = menuService;
    }

    @GetMapping               // GET /api/v1/menu
    public List<MenuItemResponseDTO> getAllItems() {
        return menuService.findAll();
    }

    @GetMapping("/{id}")      // GET /api/v1/menu/5
    public MenuItemResponseDTO getById(@PathVariable Long id) {
        return menuService.findById(id);
    }

    @PostMapping              // POST /api/v1/menu
    @ResponseStatus(HttpStatus.CREATED)
    public MenuItemResponseDTO create(@RequestBody @Valid MenuItemRequestDTO dto) {
        return menuService.create(dto);
    }

    @DeleteMapping("/{id}")   // DELETE /api/v1/menu/5
    @ResponseStatus(HttpStatus.NO_CONTENT)
    public void delete(@PathVariable Long id) {
        menuService.delete(id);
    }
}

🧠 Preguntas de Repaso — Spring Boot

¿Por qué se recomienda inyección por constructor en vez de @Autowired en el campo?
Porque facilita las pruebas unitarias (puedes pasar un mock), hace explícitas las dependencias y permite campos final (inmutables).
¿Qué diferencia hay entre @Entity y @Document?
@Entity es para bases de datos relacionales (JPA/Hibernate). @Document es para MongoDB (Spring Data MongoDB).
¿Qué hace @ComponentScan?
Le dice a Spring en qué paquetes buscar clases anotadas (@Component, @Service, etc.) para agregarlas al contexto (IoC Container).
¿Cuál es la diferencia entre @Controller y @RestController?
@RestController = @Controller + @ResponseBody. Los métodos de @RestController devuelven datos directamente (JSON) en vez de nombres de vistas.
